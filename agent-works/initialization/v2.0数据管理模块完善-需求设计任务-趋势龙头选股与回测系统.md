| DM-D7 | **任务中断恢复** | 服务重启时把残留 `running/pending` 任务标记为 `interrupted` 并保留 checkpoint，允许"续跑"（按已完成 codes/dates 跳过）。 |

| DM-D9 | **缺口判定规则** | 对每只**在市**股票，在其 `[上市日, 全局最新交易日]` 区间内：日历开市日（`trade_calendar.is_open=true`）若 `daily_bar` 无该日数据**且**该日非停牌（按 `repository.get_suspension_days/is_suspended_on` 推导）→ 记为**缺口日**；连续缺口日合并为一个**缺口段**。概览「缺口提示」展示「有缺口股票数 + 缺口日总数」，可下钻到逐股质量。 |
| DM-D10 | **质检严重度映射** | `issue_type → severity` 固定一版：`adj_jump=high`（复权跳变影响回测最直接）、`abnormal_change=mid`、`missing_or_suspended=mid`、`ohl_repaired=low`。迁移脚本按此回填旧行。 |
| DM-D11 | **数据字典维护方式** | 表/字段中文说明用**代码内置** `backend/storage/catalog.py`（不建需手维护的字典表），运行时拼 DDL 行数/最新时间；仅**维度注册表**因含"规划中"状态落 DB（`data_dimension_registry`）。 |

## 第一部分 · 需求

### 1. 背景与目标

#### 1.1 现状痛点（用户反馈归纳）
- **单页太杂**：概览卡 + 4 个任务按钮（增量更新/历史补数/重算评分/数据体检）+ 更新日志 + 质检列表 + 系统参数全挤一页；4 个按钮里 `recompute`（评分重算）、`verify`（体检）和"采集"本不搭边，排版凌乱。
- **系统参数是 v1.0 残留**：只读展示评分权重/分档阈值/流通市值区间/次新剔除/回测成本/TopN，唯一改法是**手改 `settings.yaml` 再点重载**——Web 服务却要编辑文件；且评分权重/阈值已被 `score_profile` 取代。
- **采集缺安全感**：选项太少（无指定日期/指定股票）；无**实时日志**（不知在拉哪只股哪天、进度、是否卡死）；**任务状态会卡死**（服务挂了重启后 `running` 不翻转、不记录已完成多少）；任务无交互（不能离开再回看、点开看日志）；**质检只发现不解决**（什么问题、怎么修、修没修不知道）；**定时任务无处展示**（有没有触发、进度、状态全看不到）；**并发未处理**；更新日志/质检列表一堆英文看不懂。

#### 1.2 目标
把数据管理做成「**一眼看清家底、放心采集、问题可闭环解决**」：看得清（概览+数据字典+维度注册表+逐股质量）、采得稳（异步+实时日志+进度+重启不丢+并发互斥+精细选项）、解得了（质检中文分级+单条修复+状态回写、定时可控、数据源可见）、拆得开（4 子页）、参数归位（删残留、真参迁配置管理 Web 可编辑）。
**交互总纲（用户硬性要求）**：清晰、一目了然；中文化一切面向用户的字段。

### 2. 页面总览（数据管理 → 4 子页）

| 子页 | 路由 | 一句话职责 | 对应需求 |
|---|---|---|---|
| 数据概览 | `/data/overview` | 看清家底：概览 KPI + 基础表数据字典 + 数据维度注册表 + 逐股质量 | FR-DM-1 |
| 数据采集与任务 | `/data/ingest` | 同步/补数/指定采集 + 任务中心 + 实时日志 + 续跑 | FR-DM-2/3/6/8/9/10/11 |
| 数据质量 | `/data/quality` | 质检问题中文分级 + 单条重拉/重算修复 + 状态闭环 + 一键体检 | FR-DM-4 |
| 调度与数据源 | `/data/schedule` | 定时采集开关/时间/下次触发/最近结果 + akshare·baostock 连通状态 | FR-DM-5/7 |

> 系统参数不在数据管理内，迁往**配置管理·系统设置 tab**（FR-DM-12，见 §3 与 §第二部分）。

### 3. 功能需求明细（FR-DM-*，沿用 v2.0 §3.1 编号并扩展）

- **FR-DM-1 数据概览（强化）**：① 概览 KPI——最新交易日、覆盖股票数（在市/退市拆分）、日线总行数、未解决质检数（按严重度着色）、**缺口提示**；② **基础表数据字典**——列出所有基础表（stock_basic / daily_bar / daily_metrics / index_bar / trade_calendar / data_update_log / data_quality_issue 等），每表展示中文名、作用、行数、最新数据时间、关键字段及中文说明、关联关系、质量状态；③ **数据维度注册表**——已采集维度（行情/估值/基础信息…）与规划中维度（股东数/筹码峰…）含状态徽章；④ **逐股质量**——查单股/批量关键字段达标（如 `total_mv` 非空）与鲜活度（最新 `trade_date` 是否等于全局最新交易日、是否有缺口）。
- **FR-DM-2 手动触发同步**：增量 / 全量更新，异步任务 + 进度条（已 ✅，本文并入实时日志与持久化）。
- **FR-DM-3 缺口补数（强化）**：检测指定股票/区间缺失并一键补拉；**新增"更多选项"**：指定股票列表、指定日期或日期区间、指定年限；概览缺口提示可一键带参跳转定向补拉。
- **FR-DM-4 质检与修复（闭环）**：质检问题列表**中文化 + 按严重度分级**；针对单条问题的「重拉 / 重算」操作 → 定向修复任务；问题增加状态（未处理/修复中/已解决/忽略），修复完成回写状态 + 刷新质量统计；保留一键体检（暴露 `DataVerifier` 交叉校验）。
- **FR-DM-5 数据源状态**：akshare / baostock 连通性（up/down + 最近成功时间）与基本超时/配置提示；支持手动测试连通。
- **FR-DM-6 采集日志（中文化）**：`data_update_log` 时间线展示，字段中文化（表名→中文名、source→数据源、status→成功/失败）。
- **FR-DM-7 定时采集管理**：页面开/关、执行时间（时:分）设置、下次触发时间、最近一次执行结果；scheduler 支持运行时 enable/disable/reschedule，不需重启进程。
- **FR-DM-8 页面拆分（新）**：数据管理改父菜单 + 4 子页，`/data` 重定向到概览；各页遵循 `.v-page/.v-grow/.v-scroll` 禁整页滚动契约；现有概览/任务/质检/日志能力迁移不丢。
- **FR-DM-9 实时日志（新）**：任务运行时输出逐条日志（当前在拉哪只股/哪个日期、阶段、已完成 i/N），前端可点开任务抽屉实时查看（增量轮询、自动滚动）；任务结束后日志可回看。
- **FR-DM-10 任务持久化与续跑（新）**：长任务按股票/日期粒度记录 checkpoint；服务启动 reconcile 把残留 `running/pending` 标 `interrupted` 并保留已完成进度；中断任务可"续跑"，跳过已完成部分。
- **FR-DM-11 并发控制（新）**：同类写任务互斥，创建前校验，冲突返回 409 + 当前占用任务 id；任务中心可点进详情、可离开再回来看进度。
- **FR-DM-12 系统参数迁移 + Web 编辑（新，跨配置管理）**：删 `DataView` 评分权重/分档阈值；数据源/股票池/回测成本/TopN/调度等真参迁配置管理「系统设置」tab，Web 表单可编辑；改值写 `app_config` 覆盖层，`settings.yaml` 兜底，保存即生效；表单显示当前值/默认值/是否已覆盖。

#### 3.x 范围边界
- **必须实现**：FR-DM-1（全部四项）、FR-DM-3 更多选项、FR-DM-4 修复闭环、FR-DM-5、FR-DM-6 中文化、FR-DM-7、FR-DM-8、FR-DM-9、FR-DM-10、FR-DM-11、FR-DM-12。
- **建议实现（不扩核心闭环）**：缺口提示一键跳转带参补数；实时日志导出；质检批量修复（沿用多选跨页累积标准）；任务预计剩余时间；数据源手动测试按钮。
- **暂不实现**：股东数/筹码峰等新维度的实际采集（仅注册表占位，DM-D5）；多用户/权限分级（单机自用）；免费源精确配额计量（无稳定配额 API）；历史每日 ST 还原（沿用现 `limit_status` 按板块口径）。

## 第二部分 · 设计

### 4. 架构变化总览

```
数据管理（父菜单）
├── 数据概览  /data/overview   ← 新增 catalog/dimensions/stock-quality 接口，复用 DataIntegrityReport
├── 数据采集  /data/ingest     ← 扩 IngestionService(指定日期) + task_log 实时日志 + checkpoint/续跑 + 并发互斥
├── 数据质量  /data/quality    ← data_quality_issue 加 status；fix 任务定向重拉/重算；verify 体检
└── 调度数据源 /data/schedule  ← scheduler 运行时控制 API + 数据源连通 API；配置落 app_config

配置管理（已有）
└── 系统设置 tab（新）          ← FR-DM-12：真参 Web 表单编辑，写 app_config 覆盖层（settings 兜底）
```

核心不变约束（沿用 v2.0 §10.2-C）：
- **DuckDB 单文件单连接 + `RLock`**：后台任务线程与 Web 请求共用同一连接，靠锁串行化 SQL；新任务处理器与日志写入照此模式，**勿另开连接**（文件锁冲突 IO Error）；实时日志写入需低频/批量，避免高频写阻塞轻请求。
- **失效=惰性标记**：采集/补数/修复完成只 `mark_stale_dates([受影响日期])`，绝不在写入路径同步重算；评分快照读取时按需重算（§10.1）。
- 前端改 `frontend/src` 后必须 `npm run build`；禁整页滚动契约。

### 5. 数据库变更汇总

| 操作 | 表 | 说明 |
|---|---|---|
| **新增** | `app_config` | `key VARCHAR PK, value VARCHAR(JSON), updated_at TIMESTAMP`。配置覆盖层，Web 改的值落此，`settings.yaml` 兜底；读取覆盖层优先。写入校验 key 白名单。 |
| **新增** | `task_log` | `id BIGINT, task_id VARCHAR, seq INT, ts TIMESTAMP, level VARCHAR, message VARCHAR`。任务实时日志，按 `(task_id, seq)` 递增；增量按 `after_seq` 拉取。保留策略见 DM-D8（每任务上限 2000 行、全局近 30 天、启动清理）。 |
| **新增** | `data_dimension_registry` | `dimension VARCHAR PK, name_cn, status VARCHAR(collected/planned/partial), source VARCHAR, tables VARCHAR(JSON), descr VARCHAR`。数据维度注册表（含"规划中"占位）。 |
| **改造** | `async_task` | 状态枚举增 `interrupted`（`pending/running/done/failed/interrupted`）；`params/result` 记录 checkpoint（已完成 codes/dates）。 |

### 7. 各功能设计要点

#### 7.1 数据概览（FR-DM-1）
- `overview()` 复用 `DataIntegrityReport.overview()/coverage()`；缺口提示按 DM-D9：在市股票在 `[上市日, 全局最新交易日]` 内，日历开市日无行情且非停牌记为缺口日、连续合并为缺口段，展示「有缺口股票数 + 缺口日总数」。
- `catalog`：`backend/storage/catalog.py` 内置每表元数据字典（中文名/作用/字段说明/关联），运行时补行数（`count`）与最新时间（`max(trade_date)`/`max(updated_at)`）+ 质量摘要（该表相关 `data_quality_issue` open 数）。
- `dimensions`：读 `data_dimension_registry`；股东数/筹码峰 seed 为 `status=planned`。
- `stock-quality`：聚合 SQL，逐股算 `latest_date / is_fresh(=latest_date==全局最新) / total_mv_ok(daily_metrics.total_mv 非空) / gaps / open_issues`，服务端分页，避免 N+1。

#### 7.2 采集 + 实时日志 + 持久化 + 并发（FR-DM-3/9/10/11）
- `IngestionService` 扩 `ingest_date(date, codes=None)`；任务参数 `params={codes?[],date?,date_start?,date_end?,years?}`。
- **实时日志**：处理器每处理一只股/一阶段，调 `AsyncTaskService.log(task_id, msg)` 追加 `task_log` 一行（含 code/date/i/N）；写入节流（批量提交，避免高频持锁）。
- **checkpoint**：处理器把已完成 codes/dates 写回 `async_task.result.checkpoint`；续跑时读取并跳过。
- **启动 reconcile**：服务启动时 `AsyncTaskService.reconcile()` 将残留 `running/pending` 置 `interrupted`。
- **并发互斥**：`create()` 前查同类写任务是否 `running/pending`，有则 raise 409。

#### 7.3 质检修复闭环（FR-DM-4）
- `data_quality_issue` 加 `status/severity/resolved_at`；`severity` 由 `issue_type` 按 DM-D10 映射（adj_jump=high、abnormal_change=mid、missing_or_suspended=mid、ohl_repaired=low）。
- 修复 = 新 `fix` 任务或复用 `backfill(codes=[该问题code], date)`：定向重拉该股该日期 → 完成后 `mark_stale_dates([受影响日期])` + 回写 `status=resolved, resolved_at=now` + 刷新概览统计。
- 体检 `verify` 重扫后，已被后续采集覆盖修复的问题自动消解/标 resolved。

#### 7.4 调度与数据源（FR-DM-5/7）
- `scheduler.py` 补 `enable()/disable()/reschedule(hour,minute)` 封装（现仅 start/shutdown），运行时生效；状态读 `next_run_time`、最近结果存内存/`app_config`。
- 调度配置（enabled/cron_hour/cron_minute）纳入 `app_config` 覆盖层。
- 数据源连通：复用 `backend/datasource/`，对 primary/fallback 各做轻量 ping，超时按 `socket_timeout_sec` 判 down，记 `last_success_at`。

#### 7.5 系统参数迁移与覆盖层（FR-DM-12 / DM-D2/D3）
- 新增 `app_config` 表 + `AppConfigRepo`；`backend/config/settings.py` 读取改为**覆盖层优先、settings.yaml 兜底**（合并视图）。
- `DataView` 删评分权重/分档阈值卡；其余真参分组（datasource / universe / 回测成本 / topN / scheduler）以 `GET /api/config/settings` 暴露，`ConfigView.vue` 新增「系统设置」tab 渲染表单；`POST` 保存写覆盖层，字段级校验（上界>下界、费率≥0、并发数≥1、超时>0、年限≥1、TopN≥1），保存即生效。

## 第五部分 · 风险与应对（无待确认项，全部已拍定见 §0 / §7）

> 第四部分前所有待确认点已在 §0 决策表（DM-D6~D11）与 §7 设计要点中拍定，本章仅列实现期需主动防范的技术风险与对策。

- **R-DM-1 单连接锁 vs 高频日志写**：`task_log` 写入与轻请求共用同一 DuckDB 连接，高频写会短暂持锁。**对策**：按 DM-D8 批量/节流提交（每 50 行或每 1s flush 一次），逐条 message 在锁外组装；只把成批 INSERT 放进锁内。
- **R-DM-2 续跑幂等性**：`interrupted` 任务续跑时可能重复处理边界 code/date。**对策**：续跑严格按 `result.checkpoint` 跳过已完成项；所有写入沿用 `upsert ... ON CONFLICT DO UPDATE`（已有），重复写不产脏数据；`mark_stale_dates` 幂等。
- **R-DM-3 数据源不稳定/限频**：akshare/baostock 免费源可能超时或限频，导致采集/修复任务卡住。**对策**：主备切换（primary→fallback）+ `socket_timeout_sec` 超时；单股失败记日志并继续（checkpoint 记已完成），任务整体快速失败不空转；数据源全 down 时直接失败并提示（FR-DM-5 状态卡可见）。
- **R-DM-4 评分快照失效面过大**：补数/修复波及多日时若同步重算会卡死。**对策**：严守"惰性标记"——只 `mark_stale_dates([受影响日期])`，绝不在写入路径重算；读取时按需重算（沿用 §10.1）。
- **R-DM-5 配置覆盖层越权写**：Web 可写配置存在被改写非预期 key 的风险。**对策**：`app_config` 写入校验 **key 白名单**（仅 datasource / universe / 回测成本 / topN / scheduler）；评分权重、分档阈值已废弃，不入白名单；字段级数值范围校验（上界>下界、费率≥0、并发数≥1、超时>0、年限≥1、TopN≥1）。
- **R-DM-6 破坏性迁移**：`data_quality_issue` 加列、`async_task` 状态枚举扩展涉及存量数据。**对策**：加列迁移给旧行默认值（`status=open`）+ 按 DM-D10 回填 `severity`；`interrupted` 为新增枚举值，旧值不变、向后兼容；迁移前沿用 v2.0 惯例备份 DuckDB 文件。

### 6.6 第三轮：质检-恢复闭环（M2.9.2，2026-06-13，基于用户深挖反馈）

#### 6.6.1 核对结论(真相)

- **业务判停牌靠 row-presence,不读 `is_suspended` 列**:`get_universe_asof`(当日有行情=可交易)、`is_suspended_on`、broker(无 bar 不可交易)。`is_suspended` 列恒 `False`([checker.py](../../backend/dataquality/checker.py) `add_markers`),是死列,对回测/选股零影响;**唯一**读它的是质检 `susp` 子查询([data_report.py](../../backend/services/data_report.py)),致缺口口径错误。
- **质检只覆盖 L3**:`scan_quality_issues` 仅扫 `abnormal_change`/`adj_jump`;L1 仅入库时记;**L2(`mv_missing`)从不落 issue,只有聚合**;**L4 `check_missing` 是孤儿(无人调用)**→ 质量页选「缺失」永远空。
- **修复假闭环**:`_h_fix` 一个通用动作(重拉 daily_bar 单日)+ **无条件置 `resolved` + 不复检**;对 L2(市值来自 `ingest_valuation` 非 `ingest_one_daily`)、L4 停牌(源端无数据)、L1(源端恒空)、L3 真实极端值全是假修。
- **缺口=正常停牌被误判**:`gap_days = expected − have − susp`,`susp` 恒 0 → 每个真实停牌日都算缺口;且增量只能向后补尾(`_update_one` 从 last+1 起),填不了历史中间洞,故"缺 11 条但增量 0 条"。

#### 6.6.2 关键决策(用户已确认)

- **DM-D18 反向确定停牌**:缺口**先一律按漏采处理**→ 重采该股缺口区间 → 源端**有数据=漏采(已补)**;**无数据=确认停牌**。用源端作 ground truth,不接停牌数据源。
- **DM-D19 停牌记忆表**:新表 `stock_suspension(code, trade_date)` 记"已重采确认无数据"的停牌日。**绝不往 daily_bar 插占位行**(业务靠"有行=可交易",插了污染回测)。缺口判定减去本表 → 系统收敛,gap 单调趋零。
- **DM-D20 缺口新口径**:`缺口 = 存续期开市日 − 已有行情 − stock_suspension`;弃用恒 0 的 `is_suspended` 列。L4 问题分两类:`data_gap`(疑似漏采,自带[起止日],可重采)、`stale`(尾部鲜活滞后,最新<全局最新,可增量补)。正常停牌不落 issue、不扣分。
- **DM-D21 首轮反向重采窗口**:默认 **90 个交易日**;更早历史空洞直接判停牌入表、不重采(老数据稳定,真漏采早暴露)。
- **DM-D22 恢复按类型分派 + 复检**:不同 issue_type 走不同恢复手段,**复检通过才 `resolved`**,仍在则保持 `open`+备注;不可恢复/真实极端值给「标记为正常/忽略」(`ignored`),不重采。

#### 6.6.3 四个闭环设计

**闭环 1 · 质检↔恢复**(重写 `_h_fix`,DM-D22):

| issue_type | 恢复手段 | 复检 |
|---|---|---|
| `null_close`/`abnormal_change` | 重采单日 `ingest_one_daily(code,d,d)` | 该日是否仍异常 |
| `adj_jump` | 重采该股整段 + 重算复权 | 跳变是否消失 |
| `mv_missing`(L2) | `ingest_valuation(codes=[code])`(非 ingest_one_daily) | total_mv 是否补上 |
| `data_gap`(L4) | 重采缺口区间[lo,hi] → diff;仍缺写入 `stock_suspension` | 是否还有可恢复缺口 |
| `stale`(L4) | 增量补尾 `update([code])` | 是否追上全局最新 |
| 真实极端/不可恢复 | 「标记为正常/忽略」→ `ignored`,不重采 | — |

**闭环 2 · 问题↔质检**(四层统一进同一 `scan_quality_issues`,立即/定时质检都调它):L1 防御性复扫;L2 扫 `daily_metrics` 总市值空→`mv_missing`;L3 现有;L4 逐股算缺口(减 suspension)→`data_gap`(带[lo,hi])、最新<全局→`stale`。**幂等**:每类扫描前 DELETE 上轮 `open` 自动问题再重写,`resolved`/`ignored` 不动 → 反复跑收敛不堆积。

**闭环 3 · 质量模块可操作**:质量页操作列**按类型显示正确动作**(重采区间/补市值/补尾/重采单日/重算复权/标记正常);逐股 L4 hover 显示`缺口X天[范围]`、点击带 `code+区间` 跳采集页;采集页 `onMounted` 读 query 预填 code+区间并弹"重采这段?";`指定股票采集`补区间选择;清除所有开发腔(`status=open` 等)。

**闭环 4 · 三处口径一致 + 自动刷新**:定时质检与立即质检调同一四层 `scan_quality_issues`;`quality_model`/`stock_quality` 的 L4 缺口与 scan 的 `data_gap` 用同一函数算(减 suspension)→ 概览KPI/逐股L4/质量页**数字必然一致**;概览加 `last_scan_at`;质检/修复任务完成后概览与质量页**自动刷新**。
