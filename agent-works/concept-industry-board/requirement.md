# 概念 / 行业板块功能需求

## 1. 目标与范围

把概念板块和行业板块作为现有数据管理体系中的一种正式数据类型，而不是孤立脚本。板块数据必须完整接入：数据源、采集编排、异步任务、写库互斥、日志、终止与续跑、定时任务、质量扫描、定向修复、数据目录、数据概览、CLI 和业务查询。

本功能覆盖：

- 同花顺概念 / 行业板块字典；
- 板块成分关系；
- 板块指数日线；
- 板块资金流；
- 板块列表、详情、指数走势和成分查询；
- 数据管理全链路闭环。

当前实施边界：本轮已经完成数据管理全链路、四个 `/api/sectors*` 只读接口与后端权限；`/sectors` 和 `/sectors/:boardCode` 前端业务页面、路由及 pageRegistry 仍待实施。下文页面条目是后续目标需求，不表示已经落地。

同花顺是板块数据唯一来源。行情、板块和质量台账均落 DuckDB；本功能不新增用户私有资产。

## 2. 数据源事实

- 板块主键使用同花顺 Web 路径代码 `board_code`。
- `app_code` 保存详情页隐藏字段 `clid`，供与同花顺 App 核对；概念板块通常为 88 开头，行业板块通常与路径代码一致。
- 概念资金流接口只稳定提供名称，必须按 `board_type + name` 匹配字典；无法匹配时写质量问题，禁止伪造代码或无依据新增字典。
- 指数历史接口按年份返回，源端可用历史从 2024 年附近开始；某一年请求失败只能形成部分结果，不能把该板块标记为已完整完成。
- 成分接口只提供当前快照，无法可靠还原历史退出日期。

## 3. 数据模型

只使用四张板块业务表：

| 表 | 事实口径 |
| --- | --- |
| `board_dict` | 板块字典、双代码、能力字段、最近完整成分快照时间和源快照成分数 |
| `board_member` | `(board_code, code)` 唯一；累计保存自接入以来完整快照中出现过的成分关系，只进不出 |
| `board_bar` | `(board_code, trade_date)` 唯一；板块原始连续指数日线 |
| `board_fund_flow` | `(board_code, snapshot_date, period)` 唯一；即时 / 3日 / 5日 / 10日 / 20日资金流 |

`board_dict.member_count` 是最近一次完整源快照的成分数；`board_member` 的行数是累计出现过的关系数，两者不得混称。`member_snapshot_at` 是完整快照成功证据；历史 `member_count` 不能单独证明一次失败已经修复。

不使用成分候选表，不做快照 diff，不维护 `in_date/out_date`，不做成分数量波动拦截。

## 4. 采集闭环

### 4.1 编排顺序

板块采集按以下顺序执行：

1. 字典：概念和行业分别全量 upsert，并补齐缺失 `app_code`；
2. 成分：逐板块获取完整快照，完整才落库；
3. 指数：逐板块按日期范围幂等 upsert；
4. 资金流：按板块类型和周期采集、校验、映射后幂等 upsert。

支持仅运行 `dict / members / bar / fund` 子步骤、指定板块代码和小批量 `limit`。未知步骤、非法模式、非法 limit 必须立即拒绝；指定代码不存在时必须返回失败项。

### 4.2 增量与全量

- `update` 是手动任务和定时任务默认模式：指数补最近开市日附近七个自然日，资金流只采即时；字典和成分仍按完整快照刷新。
- `backfill`：指数从 2024-01-01 起尝试回填，资金流采全部五个周期。
- CLI `board --update` 与 `board --backfill` 必须互斥；未指定时使用 `update`。
- 每日流程默认执行板块增量采集，可通过明确参数跳过。

### 4.3 成分快照安全

- 只有 `complete=True` 且非空的快照可以入库。
- 完整快照在一个事务内新增关系、刷新 `member_count`、写 `member_snapshot_at`，并解决该板块现存的 `board_member_incomplete` 问题。
- 分页失败、登录墙、空快照或请求异常时整块不落库，保留旧数据，写更新失败日志和幂等质量问题。
- 重跑只新增缺少的关系，日志中的 `added` 必须是实际新增行数。

### 4.4 指数与资金流正确性

- 指数每年请求独立记录失败年份；成功年份可落库，但任务结果必须为失败 / 部分失败，续跑不得跳过该板块。
- 资金流必须满足 `net_inflow = inflow - outflow`；缺失净流入可据此补齐，明显不一致的行不得入库并计入失败。
- 指定板块采集时，资金流写入范围也必须限制在指定代码集合内。
- 未匹配质量问题按 `board_type + name` 幂等；后续字典补齐并成功匹配后改为 `resolved`，保留审计记录。

### 4.5 任务、日志、终止与续跑

- 板块采集属于 DuckDB 写任务，与其他 DuckDB 写任务互斥。
- 字典类型、成分板块代码、指数板块代码、资金流类型+周期都必须写 checkpoint。
- 终止在当前外部请求或工作单元结束后的检查点生效；恢复时只跳过已经成功的工作单元。
- 失败工作单元不得写入完成 checkpoint。
- 任一子步骤返回失败清单时，异步任务和每日流水线步骤必须显示 `failed`，不得出现“日志失败但任务 done”。每日流水线可继续执行后续质量扫描，但整体结果为失败。
- `data_update_log` 必须记录 `success / partial / failed`、真实新增 / 写入行数、范围和错误摘要。

## 5. 质量扫描与修复闭环

板块质量类型：

| 类型 | 发现条件 | 修复动作 | 解决条件 |
| --- | --- | --- | --- |
| `board_member_incomplete` | 成分快照不完整或失败 | 定向重采该板块完整成分快照 | 新完整快照成功，且不存在该板块活动中的同类问题 |
| `board_index_gap` | 有指数能力的板块最新日早于全局行情最新交易日 | 从 2024-01-01 定向重采该板块指数 | 板块指数最新日追平全局行情最新交易日 |
| `board_fund_unmatched` | 资金流名称无法映射字典 | 先刷新字典，再重采即时资金流 | 问题详情中的名称和类型已能映射字典 |

扫描板块指数问题时必须事务化替换活动问题：新一轮计算或写入失败时保留上一轮问题，禁止先删后扫造成盲区。修复过程中使用 `fixing` 并绑定任务；异常、中断或复检未通过必须退回 `open`。只有复检通过才置 `resolved`。失败问题不得进入修复完成 checkpoint，恢复任务可以再次重试。

板块修复不影响个股评分，不得无差别让所有评分快照失效。

## 6. 数据概览、目录与健康检查

数据概览的“板块数据”摘要至少展示：

- 板块总数、概念数、行业数；
- 成分快照覆盖、指数覆盖、资金流覆盖；
- 板块指数最新交易日、资金流最新快照日；
- 活动质量问题总数及三种板块问题分项；
- 最近一次板块更新记录。

摘要点击进入板块增量采集。数据目录必须登记四张表的字段、时间字段、质量问题映射和鲜活度；`board_bar`、`board_fund_flow` 属于时间序列。数据源健康接口必须包含 `ths_board`，测试连通时实际请求一页行业字典。

## 7. 业务查询与页面目标

当前后端查询与权限已经实现，前端页面尚未实施：

- `/sectors` 支持概念 / 行业切换、今日 / 5日 / 10日 / 20日涨幅、即时资金流、上涨 / 下跌家数、排序和分页。
- `/sectors/:boardCode` 展示板块摘要、指数走势和累计出现过的成分关系。
- 涨跌幅来自最近 21 条 `board_bar` 窗口计算；列表不得为每个板块重复查询全市场涨跌家数。
- 列表和详情必须显式返回指数日期与资金流日期；无数据展示空值，不跨日期伪装“今日”。
- 接口使用 `sectors:view`，按钮和路由遵守现有 RBAC 规则。

## 8. 验收标准

1. 四表 DDL、迁移、字段目录与双代码映射一致，幂等重跑无重复。
2. `update / backfill / only / codes / limit` 行为与本需求一致。
3. 单板块、单年份或单周期失败能保留已成功数据，同时使任务诚实失败并可续跑失败单元。
4. 三类板块问题均能发现、定向修复、复检和正确收敛，失败不遗留 `fixing`。
5. 数据概览、数据目录、更新日志、任务中心、定时任务、CLI、每日流程和数据源健康均能看到板块类型。
6. 板块列表查询不存在按板块 N+1，时间窗口读取有界。
7. 本轮数据管理相关的后端专项测试、前端 Vitest、前端构建和 Playwright 用例通过；业务页面应在后续落地时单独完成页面验收。
