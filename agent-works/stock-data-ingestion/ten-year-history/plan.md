## 1. 目标与范围

采用“保留现有数据源，先修历史规则，再分批补齐十年数据”的方案，使新增历史数据能够用于看图、筛选和回测。

以任务启动时确定的最近交易日为截止日，向前推十个自然年；重试、续跑沿用同一日期范围。上市不足十年的股票从上市日起覆盖，已入库的更早数据不删除。计算起点须处理闰年边界。

| 数据 | 处理方案 |
| --- | --- |
| 个股日线、量额、换手率 | 继续使用新浪主源，BaoStock 整段兜底 |
| 复权因子、除权参考价 | 沿用获取、校准及清洗机制，查询统一使用清洗因子优先口径，不回写原始因子 |
| 逐日 ST、停牌状态 | 使用 BaoStock 历史事实，不按当前名称推断 |
| 退市股 | 纳入十年窗口内曾存续的股票，避免只补当前上市股票 |
| 交易日历、市场基准指数 | 同步覆盖十年 |
| 市值、股本 | 按源端实际可得范围补齐，缺失保持空值 |
| 分时、板块历史 | 本次不扩展 |

## 2. 执行前依据与限制

- 执行前默认 `datasource.history_years=5`；页面与后端采集参数已允许 1～30 年。
- 新浪已实测返回平安银行、贵州茅台、东方财富 2016-10-18～2026-10-16 的日线，各 2,428 条；茅台同期后复权数据可取。
- BaoStock 上述三只股票同期日线及逐日 `isST` 可取，样本 ST 字段无空值；武钢股份退市前历史、2016 年交易日历及茅台 2016～2017 年复权因子也已取到。
- 茅台现有市值接口实测仅从 2018-01-02 开始，不能据此推断所有股票具有相同起点，也不能承诺全市场十年配套数据完整。
- 历史行情补全会检查最早入库日期，已有近期数据不应直接视为完成。
- `valuation_history` 会跳过已有市值的股票，扩展既有股票历史应使用 `valuation_gaps`。
- 公共涨跌停计算尚未按日期区分创业板改革前后的普通限幅，十年范围会触及该缺口。

事实入口：`config/settings.yaml`、`backend/config/settings.py`、`backend/storage/app_config.py`、`backend/services/stock_ingest.py`、`backend/services/ingest.py`、`backend/market_rules.py`、`backend/backtest/engine.py`。

## 4. 修正历史交易规则

在全量补数之前，将公共判断统一为股票板块、交易日期及当日 ST 状态共同决定，避免直接套用当前比例。

共同消费链路包括：采集派生字段、质量检查、涨停与连板统计、筛选和回测成交限制。不得分别硬编码多份规则；同步检查 Python 与 SQL 表达式。

重点覆盖创业板 2020-08-24 前后的 10%/20% 切换；核对 IPO、退市整理等历史特殊规则。不能准确判断的日期保留明确未知状态，不当作普通交易日处理。规则依据见[深交所说明](https://www.szse.cn/aboutus/trends/news/t20200821_580924.html)。

测试覆盖切换日前后、主板 ST、科创板，以及现有五年结果是否受到意外影响；所有新增规则先核实依据再实现。

- 核查质量检查使用的目标范围，以及 README、AGENTS、采集架构中的五年事实描述。

## 7. 市值缺失与页面承接

- 每只股票分别核对实际可用范围，不用当前股本反推历史市值。
- 无市值时仍允许查看价格、量能；市值条件的筛选和评分必须明确缺失处理，不能把空值当零或默认通过。
- 区分请求失败、尚未采集、源端不可得；只有确认源端范围后才能归为不可得，不因一次空响应永久跳过。
- 避免对已确认不可得区间无休止重试；通过现有质量报告和状态提示披露缺口。
- 复用现有数据管理、新建采集任务、任务进度和质量检查入口，不新增页面或权限入口。
- 本次不做布局改造；必要的缺失提示复用现有状态组件，按局部交互风险复核，不扩展布局维护矩阵。若实施中发现必须改变页面结构，再按 DESIGN 与页面模板执行设计闭环。

## 8. 验证与完成标准

- 按上市、退市、停牌情况检查覆盖，不要求所有股票相同条数，不伪造交易记录。
- 抽查早期、中期、近期行情，与独立数据源交叉核对；核查复权及首日参考价。
- 回测使用日期均具备准确 ST 事实；创业板改革前后限幅及撮合正确。
- 重跑无重复，任务中断能续跑；失败不被记录为完整覆盖。
- 从真实入口完成跨 2020 年的回测，检查代表成交、停牌和涨跌停结果。
- 做代表性规模回归，覆盖输入加载、计算与落表，记录长区间查询耗时、内存及磁盘增长。样本指标用于估算全量，不虚构全量工期。
- 原五年查询、筛选、评分和回测完成定向回归；领域正确性不能由页面截图或 Mock 替代。
- 数据表或策略登记若有变更，同步 DDL、中文业务元数据、鲜活度及质量策略，并执行 `verify-catalog`；执行适用的数据质量检查。
- 后端测试若可能获取项目 DuckDB 锁，先按项目规则停服，结束后恢复测试前状态并确认健康。前端仅按改动风险执行定向验证，不默认全量 E2E 或构建。
- 以第三方视角自审备份、实施、失败重试、数据消费及恢复闭环，核查项目规范和事实文档同步。

历史评分快照、榜单和回测记录不批量覆盖。新增年份按需生成新结果；受数据修订影响的缓存或派生结果按既有失效机制处理，不擅自改写用户资产。

## 9. 回退与保留边界

1. 先通过现有机制终止或等待扩容任务结束，确认无写入任务。
2. 恢复代码和有效配置时保留用户其他改动，不能直接清空工作区或覆盖所有平台配置。
3. 将年限改回 5 只改变后续任务默认范围，不删除已补数据，不等于数据库回滚。
4. 确需恢复数据时，通过脚本停服并使用验证过的备份，协调 DuckDB、PG 元数据与任务运行态的一致性，再处理缓存并恢复健康状态。
5. 恢复完整 PG 备份可能回退备份后的用户资产和配置变更；执行前必须核对这段期间的写入，决定保留或迁移方式，不能静默覆盖。
6. 保留现有数据源实现与选择逻辑，本次不接入新的分钟源、不为十年前市值新增数据源。
