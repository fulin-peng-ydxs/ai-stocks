## 1. 明确三种并发，各管一件事

| 控制项 | 含义 | 已批准规则 |
| --- | --- | --- |
| 任务工作并发 | 同时处理多少只股票或工作单元 | 默认继承系统配置，允许任务显式覆盖 |
| 来源请求并发 | 同一来源同时存在多少个真实网络请求 | 跨线程、跨进程共享上限，任务不能突破 |
| 来源请求频率 | 同一来源每秒允许启动多少次请求 | 分页、重试、探活全部计入 |
| 数据库写入并发 | 同时执行多少批行情写入 | DuckDB 保持一个写入通道 |

「任务并发 6」只表示最多同时处理 6 只股票，不代表可以绕过来源请求限制。

任务页面要明确显示，例如：

> 工作并发 6，来自任务覆盖；系统默认 4。新浪当前网络请求 3，上限 4；频率上限 5 次/秒。

上述网络在途和上限是展示示例，不是已测得运行值或已确定的默认配置。

来源并发和频率必须独立控制：响应变慢时，即使每秒只启动 5 次请求，网络在途数量仍可能不断增加。

## 2. 一份来源登记，一条请求执行链路

扩展现有来源能力清单，统一登记：

- 实际来源及共享额度范围，例如新浪、东财、BaoStock。
- 支持的能力：日线、分时、股本、估值等。
- 请求频率、网络并发、超时、尝试次数、退避规则。
- 会话串行、登录、分页、数据校验等特殊约束。
- 主备切换条件，以及空响应、未发布、超出覆盖范围的含义。

AKShare 仍作为接入器，额度按它实际访问的来源计算。同一来源的接口默认共享总额度；确有证据需要区分时，增加接口限制，但仍受来源总上限约束。

所有入口，包括日常采集、补采、修复、CLI、来源测试，都走同一套执行链路：

```mermaid
flowchart LR
    A[采集／修复／来源测试] --> B[解析生效策略]
    B --> C[统一请求执行<br/>频率与并发准入]
    C --> D[来源适配与响应校验]
    D --> E[有界结果队列]
    E --> F[DuckDB 批量写入]
    F --> G[质量复检与检查点]
```

图示后半段为需要行情落库的采集、修复路径；来源测试共享前半段请求控制，结果按既有探活职责存储，不写入行情数据。

传输层统一负责网络行为，来源适配器负责接口和数据语义，业务服务负责日期、范围、主备选择和入库规则。避免各层重新实现限流、重试。

## 3. 配置统一管理，但允许来源差异

采用「通用默认值 → 来源覆盖 → 必要的接口限制」：

- 普通情况下只配置通用参数。
- 新浪、东财等可以有明确的来源覆盖。
- BaoStock 等必须串行的来源，作为能力约束执行。
- 任务只能调整工作并发，不能放宽来源保护上限。
- 页面展示最终生效值、继承来源和生效时机。

工作并发在任务启动时确定；来源频率和请求并发调整后约束后续请求，已有请求自然收敛；超时与尝试预算保持当前执行序列的一致性。

当前请求路径会反复读取、合并完整配置，改成带版本的配置快照和失效通知，避免每次 HTTP 请求都查询 PG。配置读取异常时明确显示正在使用的有效版本，不能静默切换到另一套参数。

现有 Redis 继续承担跨进程准入控制；频率和并发额度应原子判断，并处理异常退出后的额度回收。Redis 支持脚本原子执行，适合复用现有实现扩展。[Redis 官方文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)

## 4. 性能优化重点放在请求数量和数据库工作量

这是本次最值得投入的部分。

- **日线减少重复取数。** 当前不复权和后复权分别调用 SDK，重复拉取行情与流通股本。复用原始材料，评估将每股 5 次请求减为约 3 次。前提是标的识别、日期、复权、前收盘及串票防护获得等价验证，不能把同一份数据派生出的结果互相比对，当成独立校验。
- **复用网络连接。** 对可控接口使用工作线程独立、可复用的 Session，并正确关闭响应和连接；保留会话型来源的串行约束。Session 能复用底层连接，减少重复连接开销。[Requests 官方文档](https://requests.readthedocs.io/en/latest/user/advanced/)
- **取源与落库分离。** 工作线程负责取源和校验，结果经过有界队列交给一个写入通道，按数量、数据量或等待时间组成小批次。
- **市值和股本按批处理。** 提前加载目标范围内的行情及已有事实，复用现有多股票合并能力，减少逐股读取全部历史、重复 JOIN 和逐股质量扫描。
- **检查点跟随落库。** 只有数据提交成功后才登记完成；取消时停止新请求，明确处理已返回结果，保证重跑幂等。

以当前 5 次/秒计算，如果日线确实能从每股 5 次请求降到 3 次，请求间隔形成的理论下限可从约 87 分钟降到 52 分钟。这是优化空间估算，实际耗时还需要真实入口验证，不作为已承诺或已通过的性能指标。

## 5. 统一失败行为，避免越失败越慢

统一以下规则：

- 网络超时、连接错误和可重试服务错误使用有限重试。
- 限流响应触发来源共享冷却，避免所有线程一起重试。
- 鉴权失效、参数错误、明确无历史覆盖等分别处理。
- HTTP 重试、数据语义重取、任务续跑分别记账，并设置明确的工作单元总预算，避免次数相乘。
- 来源持续异常时暂缓该来源，经过少量试探再恢复。
- 主备切换继续遵守业务允许范围，不能因网络失败自动改变数据口径。

等待必须可取消、有上限、有原因；不能长期停在一句「外部接口返回后继续」。

## 6. 监控要能回答「慢在哪里」

复用现有系统配置和任务详情入口：

| 入口 | 应显示的内容 |
| --- | --- |
| 系统配置／来源状态 | 配置值、实际频率、网络在途、等待数量、响应耗时、限流与错误、冷却状态 |
| 任务详情 | 当前阶段、工作并发来源、成功／失败／跳过、有效吞吐、网络与落库积压、预计剩余时间 |
| 日志 | 阶段变化、等待原因、重试与主备切换、慢请求和慢批次 |

例如日志应能区分：

> 工作单元 6：网络请求 2、等待来源额度 1、等待落库 3。

这是单时刻互斥状态分布的展示示例，不是已测得的运行值。单个工作单元在一次网络调用结束后可转入校验、结果排队等状态；不能把同一工作单元在多个当前状态中重复累计。

数据库耗时区分等锁时间和执行时间。来源探活结果与真实采集成功率分开，避免「代表接口能连通」被理解为日线全链路健康。指标以聚合和慢样本为主，控制日志量。

## 8. 跨阶段执行与兼容边界

### 8.1 保留的数据与任务契约

- EOD 截止日、收盘／休市与源端就绪门、续跑冻结日期和范围沿用现有规则；来源优化不得写入请求区间之外或尚未收盘的数据。
- 保留点时股票池、退市股、准确逐日 ST、停牌与复权口径；不通过当前名称、当前股本或派生结果推断历史事实。
- 股本优先级、同日未复权价计算市值、独立接口市值留证及来源冲突复查沿用现有契约；计算一致不代表来源冲突已核实。
- 分时主备权限、来源覆盖和整日候选规则，板块资金流实时快照归属与分页／年度语义保持有效。
- DuckDB 写任务继续通过 `async_task` 互斥；请求治理和批量落库不能绕过任务槽位。PG 运行态与行情分库读取，不做跨库 JOIN。
- 成功、失败、跳过、部分完成和数据质量结果分别统计；网络成功不等于数据完整，日线阶段成功不等于市值与收尾全部成功。

### 8.2 配置和传输迁移

- 先保留现有配置键和显式任务并发的兼容读取，不自动把用户的 `concurrency=6` 改为系统默认 `4`，也不默认提高任何来源限额。
- 同花顺旧显式超时／尝试／退避覆盖、Cookie 优先级和 BaoStock 登录超时继续按现有契约解释；新增统一模型必须明确兼容映射。
- 迁移以能力／来源逐项切换。现有 HTTP 包装和新执行入口过渡期间避免双重限流、双重重试和重复计数；不得通过全局替换影响无关外部请求。
- 网络额度生命周期覆盖真实网络调用及响应消费／关闭边界；解析、业务计算和数据库写入不长期占用网络额度。SDK、流式响应、重定向、内部重试与跨来源请求的具体接入方式在实施时核实。
- 额度回收必须处理进程崩溃、长请求、超时和连接关闭；不能仅依赖固定到期时间，就假定旧网络请求已结束并立即复用额度。
- 来源冷却／暂停、重试等待和额度等待复用既有任务生命周期表达，不因增加监控状态擅自改变任务终态或调度触发条件。

### 8.3 页面、权限和数据结构

- 复用系统配置、来源状态及现有任务详情／调度入口；配置修改由系统管理员按现有权限和审计执行，任务覆盖从原任务编辑入口设置，监控查看复用适用的读取权限。
- 前端触发页面设计闭环：实施前读取 [DESIGN.md](../../../DESIGN.md) 和 [页面模板](../../configurable-layout-system/page-template.md)，核对配置继承、查看／编辑状态、异常、空态、迟到响应、信息降级和响应式行为。
- 组件及布局维护矩阵需要核查：[页面登记](../../configurable-layout-system/responsive-pages.md) 和 [组件登记](../../configurable-layout-system/responsive-components.md)。只在实际能力或布局变化时同步登记，不能用登记代替实现和关键视口验收；同类展示与状态逻辑优先复用。
- 若新增业务 API、功能点或可导航页面，按项目要求补后端守卫、权限 seed、按钮权限、默认角色授权决策、审计与路由扫描；禁止覆盖真实菜单配置。
- 运行指标优先复用现有任务／健康存储和 Redis 短状态。是否需要新表、具体字段和留存周期由实施时的指标规模与查询需求决定；一旦改表，必须同步 DDL、中文元数据、来源／关系、鲜活度／质量策略和 SQL 留痕，并执行 `verify-catalog`。

### 8.4 回退与运行保护

- 每阶段保持可独立验证和回退，回退不能丢失已提交行情、清空真实配置、覆盖调度或重置来源健康历史。
- 性能优化路径校验不等价时回到原有已验证取数路径；回退路径仍接受统一来源保护，不恢复不受控的线程倍增请求行为。
- 配置与结构迁移只补缺失或显式转换本次字段；专项迁移 SQL 应在本目录说明用途、执行时机、影响和回滚边界，不手工建表。
- 任何需要停服的操作先核对 `./start.sh status` 和有效运行档案；存在活动写任务时先安全收敛，不直接强杀或默认强制停服。
- 测试结束按原状态通过脚本恢复服务，并核对 `/api/health=200`；实际参数、原模式和环境身份以有效运行证据为准。

## 11. 实施结果与验收证据

### 11.1 已落地机制

- 新增统一来源登记与请求快照，通用默认值、八个来源组覆盖及 BaoStock／板块串行约束共用解析。配置批量保存使用 PG 单事务，提交后通知；每秒检查版本、最长五秒重新校验配置，读取失败保留最近有效版本并标记降级，冷启动无有效配置时拒绝外部请求。
- 真实 HTTP 发送层及 BaoStock SDK 查询共用 Redis 原子频率／并发准入；HTTP 网络槽一直持有到有界响应读取完成，SQL 不占网络槽。取消与异常释放额度；确认死亡的本机进程可回收，无法确认归属的遗留额度保守阻止超发并有界报错。
- HTTP 重试与 SDK／业务语义重试共用同一工作单元内逐 URL／方法／请求体的有限预算，自动 urllib3 隐式重试不得绕过计数。分页、不同年份和主备接口各按真实请求计数；沿用既有页数／年份及主备业务边界，不把整个任务续跑当成一次传输重试。
- 新浪日线同一次标的取源复用 Session 和三类原始材料，校验响应 JS 变量绑定的标的。日线、回填、日期重采、股本与估值路径拆为工作线程取源、主线程收口；市值优先小批合并并复用目标范围事实，异常及来源冲突仍进入原复查链路；需要额外股本事件证据时，主线程沿用原补充取源收口，不声称全部异常路径已并行取源。
- 结果队列与未完成 Future 总量受任务并发约束；批次最多 64 项且不超过工作并发，等待一秒或无在途请求时刷新；单次物理响应默认最多 32 MiB。提交失败不推进检查点，取消等待线程退出，提交后重复续跑仍沿用既有幂等合并。
- 来源页展示默认工作并发、网络上限、频率、配置版本、网络在途、等待及共享冷却；真实统计与代表接口探活分别显示。任务检查点保存网络／额度等待／数据库等锁与执行耗时，终态保留聚合结果。ETA 仅在阶段总量有效、本轮新增至少 20 项、阶段无新增技术失败时估算；缺总量的旧任务不伪造剩余时间。

配置默认值为网络并发 6、等待额度 300 秒、连续失败 3 次触发 30 秒冷却、32 MiB 响应上限；保留现有频率 5 次/秒、尝试 3 次、超时 30 秒、退避 2 秒，以及 PG 中的默认工作并发 4、既有日线调度显式并发 6。本次未以提高来源频率获取性能收益，也未覆盖用户既有配置。
