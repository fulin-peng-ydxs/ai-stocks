# 历史股市数据扩展至 2012 年计划

来源与模式：2026-11-01 用户提出“额外拉取到 2012 年，先弄一个计划”；采用普通模式；用户已在本会话批准执行，2026-11-01 开始实施。

目标与范围：在现有数据基础上，补齐完整 2012 年及之后可获取的沪深 A 股 EOD 历史，包含期间存续、后来退市的股票，以及交易日历、市场基准指数、复权、逐日 ST、股本和市值配套。上市日晚于起点的股票从上市日起覆盖，退市日及之后不补行情。

用途与归属：本文维护本次技术方案、任务顺序、验收与执行状态；需求依据为上述会话。[个股采集架构](../../architecture/stock-collection.md)、[ST 专项](../../architecture/st-status.md)、[数据管理](../../architecture/data-management.md)维护长期契约；[既有十年扩展计划](../ten-year-history/plan.md)仅作为实现和历史经验依据，不将其中旧阶段规则、数据统计或验收结论直接当作当前事实。

当前结论：本次授权补采与历史股票池修正已完成，实际行情覆盖 2011-10-31～2026-10-30。2012 年日线、准确 ST、股本与市值配套齐全；全历史无未解释缺日。真实筛选、回测、页面与备份对账已完成。仍保留明确的来源残差及原有板块问题，详见文末；不宣称全库体检全部通过。

### 推荐日期方案

- 业务验收起点为 `2012-01-01`，按真实交易日历定位该年首个开市日，不硬编码首日。
- 实施前 `datasource.history_years` 默认 10（本次已改为 15），可配置 1～30；历史行情、退市历史和股本任务已经支持 `years`，并通过 `_history_window()` 冻结实际日期。
- 推荐本次将实际生效回填年限扩至 **15 年**。以 2026 年末附近启动计算，14 年会从 2012 年年中或年末附近开始，漏掉年初；15 年可完整覆盖 2012 年，并附带部分 2011 年数据，附带历史保留。
- 15 年仍是滚动窗口，不承诺永久固定在 2012 年。此次采入的更早记录不主动清理，历史质检已有覆盖“配置窗口与更早已存历史”的逻辑。若要求“严格只采 2012 年起”或“今后新库始终从 2012 年起”，须改为固定起点方案并调整任务/配置契约，本计划不预先增加这套能力。
- 首个正式任务确定上界 E：按北京时间、真实交易日历及源端就绪规则取得最近可采的已收盘交易日。后续阶段必须使用同一 E；续跑不得随跨日或配置变化漂移。各股票再按上市、有效退市及停牌事实裁剪。
- 2012 年初的 MA250、HHV480 等需要更早行情预热。15 年窗口附带的数据未必足以满足最长窗口；本次按实际可得行数返回不足/不适用，不承诺从 2012 年首日即可运行所有长周期策略。要求首日全部指标可用时，须另行向前补足共享指标引擎要求的交易日数。

## 2. 实施方案与任务

### 共用入口与执行顺序

复用 `POST /api/data/tasks` → `stock_ingest` 参数白名单 → `IngestionService` → 现有数据源、清洗与仓储 → 统一质量检查；源端请求复用共享限流、重试和 BaoStock 执行器。所有正式采集及修复写库任务进入 `async_task`，不在服务持锁时另起 CLI 写 DuckDB。

顺序为 T1 源端核验 → T2 备份与运行准备 → T3 样本及全量补采 → T4 对账与业务验收。测试、备份与正式采集分开占用数据库，正式各阶段串行执行，不额外创建调度或自动轮询。

### T1：确认 2012 年来源覆盖与目标股票范围

对应 L1、L2；依赖：无；状态：已完成；验收：V1-01、V2-01。

**目标与现状依据**

`backend/services/stock_ingest.py` 已有 `history_backfill`、`delisted_history`、`share_capital_history`、`valuation_gaps`、`st_status_refresh` 等方案。`backend/services/ingest.py` 的历史服务及 `backend/services/history_quality.py` 已处理窗口、上市退市与准确停牌边界。既有十年采集成功不能证明 2012 年各字段均可取。

**实施方案与步骤**

1. 从当前基础资料选取 2012 年前已上市的沪市主板、深市主板、创业板样本，另覆盖历史 ST、长期停牌、A/H 股、换码/吸收合并及 2012～原历史起点之间退市的股票。科创板及后来上市股票验证上市前不造数。
2. 用现有来源适配器真实读取 2012 年初、年中、年末以及原历史起点前后数据，核验不复权价格、后复权因子、前收盘参考价、逐日 ST/交易状态、股本事件及指数日线。主/备用源分别记录覆盖、失败和证据，不把同次材料复用当独立交叉验证。
3. 对退市名单、上市退市日期及库内历史标的作并集核验，形成按存续区间确定的目标清单；不得只对当前在市股票补数。核对源列表遗漏、代码变更及人工维护日期保护。
4. 核对既有特殊交易日与 IPO 首日适用性规则对新增年代的处理。来源不返、状态未知、价格冲突分别记录；不以空响应认定停牌，不以涨幅反推不限幅日。确需新增规则时先找权威依据，复用 `backend/market_rules.py` 和既有特殊日事实，不在采集或回测处重复硬编码。

**产出与完成条件**

将样本覆盖、目标池口径及失败分类回填本任务；确认关键来源具备继续试跑条件。网络故障采用既有有界重试；关键日线、ST 或退市覆盖无法核实则阻止相关全量阶段，不用更大批次反复试错。实际结果：2026-11-01 真实抽样通过，详见下方当前实施证据。

### T2：备份、容量与配置准备

对应 L1、L4、L5；依赖：T1；状态：已完成；验收：V1、V2-02、V5。

**目标与现状依据**

实施前 YAML 与 Pydantic 默认均为 10 年；PG `app_config` 可以覆盖。`_history_window()` 冻结起止，但不同任务各自新建时仍可能选到不同上界。现有后台为 dev；2026-11-01 只读检查 PID 与运行档案一致、环境标记为 dev、健康检查 200，此信息不替代执行当日复查。

**实施方案与步骤**

1. 重新执行 `./start.sh status`，核对可信运行档案和在途任务；记录原运行方式、配置版本和调度状态，不记录凭据。等待写任务收尾，不强制中断其他任务。
2. 按脚本安全停服，完成 DuckDB checkpoint 后备份实际数据库及必要旁文件；同时备份 PG 中本次将影响的配置、任务与审计运行态，记录一致性时点。备份放项目外独立业务目录，记录路径、大小、校验和及可恢复性检查结果。
3. 读取当前全库与分年度行数、股票数、最早/最晚日期、各股票覆盖、ST/股本/市值缺失、质量问题和源核验提醒。记录配置基准与行情重叠区校验基线，不能引用十年计划旧数字替代。
4. 由样本实际新增行数、文件增长、耗时及峰值内存推算全量；核算备份、数据库增长、WAL/checkpoint 和临时查询空间。可用空间不足以容纳备份与实测推算的峰值时先停止，不冒险启动全量；基线和估算差异过大则重新测量。
5. 在获得实施授权后，将 `config/settings.yaml` 与 `backend/config/settings.py` 默认扩为 15，检查 PG 是否有显式年限覆盖。目标环境通过既有系统设置机制保存生效值及审计，不通过 seed 覆盖。同步默认值断言与有关说明；只改默认时不增加 DDL、菜单或权限。
6. 按原模式恢复服务并核验健康。正式批次记录统一 E、实际起点及目标清单。优先使用现有任务日期/checkpoint 能力；若无法通过现有编排把同一 E 安全交给后续任务，扩展共享窗口传递后先完成定向验证，禁止手工篡改检查点或直接改任务表凑范围。

备份可校验，容量可支撑试跑，真实生效值可核实，原调度开关保持原状态，批次统一日期有可执行传递方式。默认扩大将影响后续未显式指定年限的新建历史任务及历史复查，须回归这些消费方；已有冻结任务继续使用原窗口。实际结果：备份、容量基线、15 年配置及统一截止日已完成并通过定向回归，具体路径、校验和与运行状态见文末实施证据。

本次基线方案不新增页面、控件或布局，沿用现有年数设置与任务页面，故不触发页面设计/组件布局维护矩阵变更。业务入口的使用验证已完成；若实施中需要改变页面交互，须先补适用设计方案与验证安排。

### T3：小批试跑后，分阶段补齐历史

对应 L1～L4；依赖：T1、T2；状态：已完成（保留明确来源残差）；验收：V2、V3。

**实施方案与步骤**

1. 先以 T1 的代表性股票完整运行获取、清洗、ST、落库、复权收尾、股本及质量检查。退市股方案通过本次扩展的 `codes` 共享筛选点运行小批试采，API 白名单与分派同步；不能给 API 传白名单外字段。证明试跑可恢复后才全量。
2. 补真实交易日历、配置的市场基准指数和基础日期，再运行在市股 `history_backfill`；按逐股覆盖判断跳过已覆盖股票。指数按真实可得历史判断，晚成立指数不伪造 2012 年值，追溯发布历史也须保留来源语义。
3. 运行 `delisted_history`，覆盖目标窗口内存续的退市股，尊重人工维护的有效摘牌日期。对在市与退市目标集合分别对账，不以当前名册数量充当全部历史标的数量。
4. 日线先取得准确逐日 ST；必要时通过 `st_status_refresh` 定向补齐并完成现有发布门验证。运行 `share_capital_history` 覆盖已有日线中的在市及退市股票，再用 `valuation_gaps` 修复剩余市值缺口；不得用 `valuation_history` 的“整股已有市值即跳过”判断新增年代已齐。
5. 复权收尾沿用既有序列重建机制，保留源因子、有效前收盘及独立参考价。`adj_factor_clean` 可因更早序列重建而变化，但必须核验重叠区收益连续性、除权与换码衔接，不能将所有差异一概认作正确。
6. 每阶段核对目标、成功、已覆盖、失败、未完成及实际日期，写入本计划任务结果并引用任务 ID。单股失败按现有机制保留已提交数据和断点，整阶段完成判据不因“任务终态已结束”自动满足；技术错误先修复并续跑，来源无数据须保留证据和质量缺口。

**性能、并发及失败恢复**

- 当前历史回填可能对未覆盖股票重新获取整个目标窗口，不能把新增约四年历史误算成只传输四年数据。先测网络与落库开销，再决定是否有必要在共享入口优化缺口拉取；任何优化均需验证复权衔接与旧数据保护。
- 沿用有界网络并发、来源共享限额和 DuckDB 单写通道；并发从目标环境当前安全值开始，以失败率、额度等待、内存和落库耗时判断，不盲目使用最大并发。
- 每个新阶段复核 E。阶段严重失败、持续来源故障、空间不足或重叠区异常时暂停后续阶段；协作取消当前任务，保留已提交数据，完成诊断后从原冻结窗口续跑。
- ST 沿用准确逐日事实；股本按来源历史变更日期生效，公告仅作溯源。市值优先同日股本乘未复权收盘价，接口市值单独保留核验；不以当前股本倒推，不填零，不把来源冲突掩盖为已核实。

**完成条件与当前结果**

目标集合均有可对账结果，无未解释漏采；必要 ST 与复权收尾完成，股本市值完成采集及缺口分类，满足 V3。来源真实不可得的字段可以形成明确残差交付，但不能宣称全字段齐全。实际结果：在市与退市行情补采、准确 ST、特殊日、复权及股本/市值配套已完成；全库缺日、字段缺失、公式不一致和 dirty 因子均为 0。来源拒用与一条历史价量错配未冒充修复成功，任务与证据见最终交付。

### T4：全历史对账、研究入口验证与交付

对应 L2～L5；依赖：T3；状态：已完成（全库未通过项及来源提醒见最终交付）；验收：V3、V4、V5。

1. 复用 `HistoryQualityService`、`CapitalQualityService`、统一采集收尾和结构体检，逐年核对交易日历×存续股票应有日期，排除准确停牌；不得只看近 90 日质量摘要。日历自身须先确认完整，避免日历缺失使行情缺口被掩盖。
2. 与 T2 基线对比重叠区：原始 OHLC、成交量额、源因子、前收盘参考价、股本市值及记录缺失。非预期改动必须逐类解释并处理；合法来源修正保留证据，不要求清洗字段机械不变。
3. 用既有真实 API 验证 2012 年看图与同日股本市值、指标计算、筛选和包含退市标的的点时股票池/回测。复权消费统一现有有效因子入口，交易判定仍用原始价，T 日信号按 T+1 成交；预热不足按共享引擎规则处理。
4. 数据修订后验证指标/查询缓存输入版本确实变化；已有评分、筛选或回测记录按各自版本及快照语义保留，验证新跑可读取新增历史，不自动覆盖用户历史资产。
5. 仅修复本次暴露的同根因问题，补足必要边界测试；实际影响 DDL/表元数据时同步目录及 SQL 归档后执行 `verify-catalog`。更新受影响 README 与采集架构，将“默认 10 年”改为实际新事实；旧十年计划作为历史成果保留，不重写其验收数字。

完成条件：验收逐项有证据，残差按股票/日期/字段/原因列出；服务恢复原可信模式并健康，任务与调度状态明确。实际结果：最终行情/股本/市值和备份对账、历史股票池、2012 年页面及普通账号筛选/回测均完成；原有 PG 研究资产、配置和调度逐行一致，原 dev 服务已健康恢复。
