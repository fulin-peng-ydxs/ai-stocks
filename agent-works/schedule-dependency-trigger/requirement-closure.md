# 任务调度依赖触发需求闭环

归档状态：已归档

## 需求目标

在现有按时间触发的任务调度之外，增加按任务执行结果触发的依赖模式，使数据更新、质检、修复等任务可以组成可靠的自动执行链；依赖命中后支持延迟执行，并通过有上限的自身重试完成受控循环。

## 用户与入口

- 使用者沿用现有任务调度管理权限 `data-schedule:manage`，从「数据管理 → 任务调度」进入。
- 不新增页面、菜单或权限资源；在现有任务列表、新建/编辑弹窗和业务抽屉中完成配置、观察和追踪。

## 完整业务闭环

1. 用户创建或编辑调度任务，触发方式在「按时间」和「按任务依赖」之间二选一。
2. 依赖任务选择一个上游调度任务，并选择成功后、失败后或完成后触发，以及固定延迟。
3. 上游通过时间、立即执行、依赖或续跑进入终态后，系统按任务身份和本次执行尝试判断条件。
4. 条件命中时生成可恢复的待触发事件；延迟到期且执行资源可用后创建下游异步任务。
5. 下游任务可配置自身循环条件、独立重试延迟和最大重试次数；条件持续命中时重复执行，条件不命中、人工终止或达到上限时结束。
6. 用户可从任务调度页查看等待状态和触发记录，从任务中心查看实际执行任务、日志、进度与结果。

## 核心规则

- 触发方式互斥：一条任务只能按时间或按一个上游任务触发。
- 一个上游可带多个下游，支持多级依赖；普通依赖必须无环，保存时拒绝直接或间接循环。
- 同一上游命中多个下游时，每个下游独立生成持久化触发事件，不因其它下游正在执行而丢失。支持从上游查看完整直接下游并拖动排序后统一保存；事件按实际到期时间、批次生成时间和生成时的顺序快照依次尝试分发。调整只影响新事件，不保证前项完成后才启动后项；不同延迟配置可能改变执行先后。
- 自循环不作为普通依赖边，而是任务自身的受控重试策略。
- 成功后仅匹配 `done`；失败后仅匹配 `failed`；完成后匹配 `done` 或 `failed`。
- `interrupted` 不触发下游，也不触发自身重试。
- 所有通过调度定义产生的执行来源都参与判断，包括定时、立即执行、依赖、重试和失败后续跑；没有调度任务身份的独立手工任务不参与匹配。
- 续跑沿用同一异步任务，但每次运行尝试独立产生终态事件，保证失败后续跑成功可以分别驱动对应分支且每次尝试不重复消费。
- 依赖首次延迟与自身重试延迟分别配置，均使用非负整数加秒、分钟、小时单位；`0` 表示立即，换算后最大 30 天。
- 延迟和最大重试次数只接受整数或整数等价值，拒绝小数、布尔值和非有限数，不做静默截断。
- 最大重试次数不含首次执行；启用后允许 `1–20` 次。达到上限只结束调度链，不改变最后一次异步任务的真实结果。
- 依赖与重试事件在写任务并发槽位被占用时等待，不得像普通时间触发一样跳过。
- DuckDB 写任务全局单写互斥：同批到期的多个写下游串行执行，后续事件保持等待并周期重试；只读任务和仅写 PostgreSQL 的任务不占用该槽位，可与 DuckDB 写任务或彼此并行。
- 停用任务取消尚未被分发器认领的等待事件，已完成认领并创建的运行任务不强制终止；重新启用不回放历史事件。页面在存在等待事件时必须提示取消数量和不可恢复语义，由用户二次确认。
- 已进入等待的事件使用生成时配置快照；编辑任务只影响新事件。仍被依赖的上游任务禁止删除。

## 页面闭环

- 任务列表展示触发方式、触发规则、自身重试摘要、等待状态和下一计划触发时间。
- 新建/编辑弹窗按触发方式显示时间配置或依赖配置，并提供自身重试开关和完整校验反馈。
- 「立即执行」绕过时间和上游条件直接运行当前任务，但运行结果仍参与自身重试和下游传播。
- 「下游任务」抽屉展示直接下游的名称、类型、启停、条件和延迟，拖动或键盘调整草稿后统一保存；保存冲突提示刷新，保存失败保留草稿，关闭未保存修改时确认放弃。
- 「触发记录」业务抽屉展示来源任务、来源结果、命中规则、计划/实际时间、等待/取消/耗尽状态、重试序号和下游任务 ID。
- 加载、空状态、错误、权限不足和保存失败沿用现有页面四态与权限处理；依赖冲突和循环链路必须给出可理解的错误信息。

## 失败处理与恢复

- 任务终态与待触发事件原子写入，服务重启后恢复等待事件。
- 写任务创建须在同一进程互斥区间内完成幂等查询、全局写槽位检查和 `pending` 落库，避免手工、时间与依赖线程同时通过检查。
- 事件认领、目标启停/删除和任务创建使用同一事件锁串行化：停用先完成则事件取消，分发认领先完成则任务视为已触发，后续停用不反向终止运行任务。
- 调度定义的新建、依赖修改和删除也共用关系锁，保证循环/引用校验与写入不可交错，禁止产生删除上游后的悬空依赖。
- 延迟已到期的事件在恢复后尽快执行；执行资源繁忙则继续等待。
- 一对多下游中的单个事件分发失败、取消或耗尽，只影响该下游事件，不连带取消同一上游产生的其它下游事件。
- 同一来源任务、执行尝试、目标任务和规则只生成一次事件。
- 分发过程中异常退出的事件在启动时恢复为可重试状态。
- 达到自身重试上限后记录耗尽原因并停止，不再创建新任务。

## 范围划分

### 必须实现

- 时间与单上游依赖两种触发模式。
- 三类结果条件、延迟触发、可靠等待、多级无环依赖。
- 可配置结果条件、独立延迟和最大次数的自身重试。
- 运行链与触发事件留痕、页面配置和触发记录反馈。
- 存量时间任务兼容、权限复用、相关测试和事实文档同步。

### 建议实现

- 本次纳入：任务列表展示最早等待时间和等待数量，便于判断链路是否正常推进。
- 后续建议：依赖关系图形化展示；当前列表和触发记录已能完成配置与排障闭环。

### 暂不实现

- 多上游 AND/OR 汇聚与批次匹配。
- 任意跨任务循环，如 `A→B→C→A`。
- 指数退避、超时分支、补偿任务和人工审批节点。
- 对没有调度任务身份的独立手工任务按任务类型模糊匹配。

## 已确认结论

- 时间与依赖触发二选一。
- 每条任务只依赖一个普通上游。
- 所有通过调度定义产生的执行来源均可传播。
- 人工终止不属于失败或完成条件。
- 延迟采用数值加单位。
- 支持多级链路，普通环路禁止，以自身重试满足受控循环。
- 最大次数按额外重试次数计算，重试使用独立固定延迟。
