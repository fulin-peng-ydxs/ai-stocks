# 需求文档：交易纪律记录与履约打卡

> 需求状态：业务闭环及审查阻塞项已确认，可作为开发计划输入  
> 确认日期：2026-08-21  
> 页面原型：[prototypes/trading-discipline-workbench.html](prototypes/trading-discipline-workbench.html)

## 1. 背景与目标

「复盘啦」已经具备行情、评分、筛选、买卖指标、回测和盘感训练能力，但缺少面向真实用户的交易纪律记录工具。用户目前无法在系统中事先记录自己的选股与买卖规则，也无法在每个交易日确认是否履约、保存实际操作并持续复盘。

本需求新增“交易纪律”业务模块，完成以下目标：

1. 将用户的本金、选股规则、买入规则和卖出规则结构化、版本化保存。
2. 支持多套交易规则按真实交易日分别履约打卡。
3. 同时覆盖“已履约/未履约”“有操作/无操作”“有成交/应操作但未执行”等真实场景。
4. 保存股票、操作方向、规则关联和可选成交财务数据，为后续交易可视化、回报率分析、规则引擎判断和 AI 分析提供可靠原始事实。
5. 在正式工作台之外，通过现有用户中心全局抽屉提供全局状态和快捷无操作打卡入口。

本期是记录与履约闭环，不自动给出买卖建议，不自动裁决履约，不生成收益图或 AI 结论。

| 能力 | 当前事实 | 本需求使用方式 |

| 用户中心 | `frontend/src/App.vue` 顶栏头像打开 440px 视口级用户中心抽屉，目前只承载身份和退出登录 | 增加“今日交易纪律”快捷卡片；完整表单仍在正式页面 |

### 2.2 现有能力与新功能边界

- 现有“买卖指标”是由技术指标条件树组成的量化方案，用于个股信号和回测；本需求的“交易规则”是用户书写并每日履约的个人纪律，两者不得混用同一业务表或以名称直接关联。
- 行情和股票参考数据继续存放 DuckDB；用户规则、履约、操作和未来分析结果存放 PostgreSQL。服务层分别取数后合并，禁止跨库 JOIN。
- 当前没有可证明的真实业务数据库样本可供本需求统计，需求只依据代码、DDL、架构文档和用户确认结论，不假设现有用户已经有交易纪律数据。

## 3. 用户角色与使用场景

### 3.1 角色与数据范围

| 角色 | 能力 | 数据范围 |
| --- | --- | --- |
| 普通用户 | 查看页面、维护自己的规则、提交和修正自己的打卡 | 仅当前 `tenant_id + owner_user_id` |
| 租户管理员 | 与普通用户相同；管理身份不扩大私人交易数据可见范围 | 仅本人，不可查看租户其他成员 |
| 系统管理员 | 具备全部功能码，但业务查询仍以本人资产为默认范围 | 不提供查看他人私人交易记录的业务入口 |
| 无角色/无授权用户 | fail-closed | 菜单、路由、快捷卡片和接口均不可用 |

本期不支持规则公开、租户共享、管理员代填或团队监督。

### 3.2 典型场景

- 首次使用：创建“趋势账户”规则，填写 20 万本金、三条选股资金计划和买卖纪律，校验通过后启用。
- 每日无操作：最新交易日没有符合条件的标的，从用户中心快捷确认“今日无操作，已履约”。
- 每日有操作：进入工作台，记录买入股票和成交数据；每笔操作分别关联一条具体选股规则和一条方向匹配的具体买卖规则。
- 未履约无成交：本应止损但没有卖出，选择“未履约”，填写“应执行但未执行”，操作记录可为空。
- 多规则：同一交易日分别对“趋势账户”和“试验账户”打卡，互不覆盖。
- 历史修正：发现昨天选错关联规则，修正后保留首次提交时间、修订号和旧修订事实。
- 未来分析：规则引擎或 AI 对指定规则版本、打卡修订和行情截面生成独立判断，不改写用户自评。

## 5. 详细功能需求

### 5.1 R1、R2、R3、R16：交易规则生命周期

- **规则主体字段**：规则名称、总本金、状态、当前版本、创建时间、更新时间。
- **规则名称唯一**：同一 `tenant_id + owner_user_id` 下全部未删除规则名称经 I2 归一化后唯一，草稿、启用和归档状态共同参与校验；复制默认生成“原名称-副本”，冲突时递增数字后缀，用户仍可修改。
- **选股规则明细**：稳定明细标识、规则名称、最大资金、支持回车换行的规则内容、展示顺序、启用状态。
- **买卖规则明细**：稳定明细标识、规则名称、一级类型、二级类型、支持回车换行的规则内容、展示顺序、启用状态。一级与二级类型采用受控映射：买入只能选择“建仓/加仓”，卖出只能选择“清仓/做T”；切换一级类型后，二级类型候选立即切换，原二级值不合法时必须清空并要求重新选择。
- **规则内容编辑**：选股和买卖规则内容必须使用多行文本编辑器，保留用户回车和空行，按原换行语义保存；编辑态自动换行并完整展示，不使用单行输入、横向滚动、ellipsis 或悬浮提示替代正文。正文很长时由规则管理右侧工作区按页面布局正常滚动，不能把内容静默截断。
- **状态流转**：`draft（草稿） → active（已启用） → archived（已归档）`；归档后可重新启用。
- **启用条件**：规则名称非空；本金大于零；至少一条启用的选股规则、一条买入规则和一条卖出规则；全部资金校验通过。
- **资金校验**：所有金额以人民币元保存，最多两位小数；每条启用选股规则最大资金 `> 0` 且 `<= 总本金`；全部启用选股规则最大资金之和 `<= 总本金`。草稿保存允许暂时不完整，但必须即时显示剩余可分配金额；启用和正式保存生效时后端重新校验。
- **版本规则**：草稿首次启用形成 v1；已启用规则发生名称、本金、选股规则或买卖规则的实质变化时产生新版本；无实质变化不新增版本。每个正式版本记录启用时的 `effective_from_trade_date`，取启用动作发生时系统最新数据交易日；同一规则同一生效交易日多次启用时，仅最后一次启用版本作为该日后续补录的有效版本，已经提交的旧打卡仍保持原绑定版本不变。
- **归档与删除**：已形成正式打卡的规则不得物理删除，只能归档；尚未启用且没有打卡的草稿可以删除。归档不删除版本和历史打卡。
- **复制**：复制当前可见版本为本人新草稿，副本从 v1 开始，不复制打卡、操作和历史修订。
- **异常反馈**：资金超限必须同时指出超限金额和对应规则；保存冲突、版本已变化或规则已归档时保留用户输入并允许刷新后重试。

### 5.2 R4、R5、R26、R27、R30：履约打卡

- **唯一业务口径**：同一用户、同一规则主体、同一交易日只有一条打卡身份；修正形成新修订，不新增第二条并行记录。
- **日期**：默认 `GET /api/data/trade-dates` 返回的 `max`；只允许选择 `dates` 中 `<= max` 的日期，不允许未来日和非交易日。
- **历史补录版本**：选择早于最新交易日的日期时，只能绑定该规则 `effective_from_trade_date <= 履约日期` 的最后生效版本；没有有效版本时禁止补录并提示“该日期尚无生效规则版本”。已经存在正式打卡时继续读取其原绑定版本，不因当前版本变化而重算。
- **用户自评**：`complied（已履约） | breached（未履约）`，由用户人工选择，系统不得自动覆盖。
- **操作状态**：明确选择“今日无操作”或填写至少一条操作。两者互斥；已有未提交操作时切换无操作必须二次确认并清空当前会话输入。
- **未履约原因选择**：使用一个可输入的单选下拉框，未履约时必须且只能确定一个原因。用户既可从已有原因中选择，也可直接在同一控件内输入文字，不设置独立的“新增”按钮或“管理原因”面板。系统提供冲动交易、未按选股规则、未按买入规则、未按卖出规则、超出资金上限、应执行但未执行、计划外操作、其他等内置原因；内置原因只读，不允许用户删除或改名。
- **自定义未履约原因**：提交打卡时，后端按去除首尾空白、不区分大小写和全半角归一口径匹配当前用户可用原因；匹配到已有项则直接复用，匹配不到则在同一事务中新增为当前用户的个人原因并用于本次打卡。输入不能为空；保存失败时保留输入并明确提示，不能先新增原因却让打卡失败后留下孤立变更。
- **原因删除**：下拉展开列表中的每条个人原因直接显示删除入口，不再跳转或展开其他管理区域；内置原因不显示删除入口。删除前二次确认；删除只使该原因不再出现在本人后续候选中，已经提交的历史修订继续通过原因名称快照完整展示。若删除的是当前已选原因，确认后清空当前输入并要求重新选择或填写。
- **详细说明**：选择“未履约”后展示独立多行“详细说明”，必须填写，支持回车和完整换行；用于说明发生了什么、为何未履约及后续如何改进。它不是某个原因的名称，也不因删除自定义原因而消失。
- **已履约无操作**：合法，表示当日没有符合交易条件或无需操作，但用户遵守了纪律。
- **未履约无操作**：合法，用于“应当操作但未执行”等场景，仍必须填写原因。
- **提交状态**：首次正式提交为 `submitted`；后续提交为 `amended`，保留首次提交时间、当前修订号、最后修正时间。
- **无打卡草稿**：本期不创建、读取、删除或冲突检测任何服务端打卡草稿。提交前内容仅存在当前前端会话；离开或切换上下文时按 R17 提醒。规则生命周期中的 `draft` 只指交易规则草稿，与打卡无关。
- **快捷提交**：全局抽屉仅允许提交“已履约 + 今日无操作”；必须展示规则、交易日并二次确认。若已有正式记录、规则归档或日期不可用，则跳转正式页面处理，不直接覆盖。

### 5.3 R6、R7、R8、R31：操作记录与规则关联

- 每条操作拥有独立标识和顺序；同一股票同一天允许多条买卖，不能按股票去重。
- 股票通过 R31 专用端点按代码/名称远程搜索选择；保存股票代码和提交时名称快照。代码是行情关联键，名称快照服务历史展示。
- 操作类型为买入或卖出。
- 每笔买入或卖出操作都必须单选一条该版本的启用选股规则，不再使用多选；选股规则候选不按买卖方向过滤。
- 每笔买入操作必须单选一条该版本的启用买入规则，候选同时展示二级类型“建仓/加仓”；每笔卖出操作必须单选一条启用卖出规则，候选同时展示二级类型“清仓/做T”。
- 具体选股规则与具体买卖规则使用相同选择逻辑：当前候选恰好一条时系统自动选中；候选多于一条时保持未选择并要求用户明确选择，禁止默认取第一条；候选为零时显示规则版本配置异常并阻止提交。
- 两个选择器都只能关联当前打卡所绑定规则版本中的启用明细，不得关联其他规则主体、其他版本或已停用明细。
- 用户切换操作方向时，具体选股规则保持不变；若已选具体买卖规则方向不再匹配，则按新方向重新计算候选：唯一候选自动选中，多候选清空并要求选择，不能静默保留错误关联。
- 可选财务字段为成交价格、成交数量、成交金额、交易费用、操作时间和说明。价格、数量、金额、费用不得为负；时间必须落在履约交易日。
- 价格与数量齐全时前端可提示计算金额；用户填写的成交金额与计算值明显不一致时提示确认，但本期不替用户篡改。仅填写成交金额也允许保存。
- 财务字段不完整不阻止履约打卡；历史详情必须展示数据完整度，未来收益图不得把不完整记录当作精确成交。

### 5.4 R9：历史、详情和修正

- 历史列表支持交易日期范围、交易规则、履约结果、是否有操作、股票、违规原因和是否修正筛选。
- 默认按交易日倒序、最后修改时间倒序，服务端分页。
- 列表展示交易日、规则名称与版本、自评结果、操作数量、违规摘要、修订号、最后更新时间。
- 详情展示该修订下的规则版本快照、用户自评、原因、说明、全部操作和规则关联。
- 修正以当前修订为起点创建新修订；旧修订不可变且可在详情中查看。
- 正式打卡不提供物理删除入口；错误记录通过修正收敛。本期没有打卡草稿及其删除入口。

### 5.5 R10、R11、R28、R31：参考数据、权限与归属

- 新页面固定路由 `/trade-discipline`，作为独立一级业务菜单“交易纪律”，不放入系统配置。
- 功能码固定区分：`trade-discipline:view`（页面与摘要）、`trade-discipline:rule-manage`（规则维护）、`trade-discipline:checkin-view`（履约和历史读取）、`trade-discipline:checkin-submit`（提交与修正）。系统角色恒过；普通用户和租户管理员默认授予全部四项；无角色 fail-closed。
- 后端所有业务端点挂精确资源码并通过现有无守卫路由扫描测试。
- 菜单 seed、资源 seed、默认角色授权、存量角色补授权和 `perm_ver` 自增必须形成同一迁移闭环。
- 前端菜单来自后端；按钮按功能使用 `v-permission`；路由守卫按授权菜单判定。
- 用户中心快捷卡片只有同时拥有页面查看和履约查看权限时展示；快捷提交按钮还要求履约维护权限。
- 所有 PG 主体、版本、打卡、修订、操作和关联查询均带 `tenant_id + owner_user_id`；归属只取请求上下文。
- 新增 `GET /api/trade-discipline/stock-options?q=...&limit=...` 轻量股票选择端点，使用 `trade-discipline:checkin-submit` 守卫，不依赖 `stocks:view`。端点复用现有 DuckDB 股票参考数据查询能力，只返回代码、名称、板块、行业，`limit` 受控且最大 20；不得返回行情详情、自选分组或其他 `stocks:view` 能力。现有 `GET /api/stocks` 保持原权限和用途不变。

### 5.6 R12、R13：用户中心快捷入口

- 在现有用户中心抽屉身份卡下方增加“今日交易纪律”卡片，不创建第二套全局抽屉。
- 卡片展示最新交易日、启用规则数量、完成数量、待打卡数量，以及每套启用规则的状态。
- 用户头像在存在待打卡规则时显示非阻塞状态点；加载失败、无权限或没有启用规则时不显示误导性红点。
- 规则行提供“去打卡”；待打卡且无冲突时提供“无操作履约”快捷动作。
- “去打卡”关闭用户抽屉并进入 `/trade-discipline?tab=checkin&rule_ref=...&trade_date=...`。URL 只恢复会话态，不写用户偏好。
- 快捷提交成功后立即刷新抽屉摘要和工作台对应状态；失败保留抽屉现场并提供重试或进入正式页面。
- 用户中心不承载股票搜索、多操作录入、未履约原因或规则编辑，避免 440px 全局抽屉成为长流程表单。

### 5.7 R14：后续分析的数据边界

- 用户输入的规则、打卡、操作和修订属于原始事实，提交后旧版本不可变。
- 未来规则引擎判断和 AI 判断必须作为独立派生结果保存，至少关联规则版本、打卡修订、行情截面日期、判断器/模型版本、输入版本、结论、证据和生成时间。
- 用户自评、规则引擎判断、AI 判断三者并存；派生判断不得改写用户自评。
- 分析结果可按输入签名重算；模型或规则变化后生成新结果，不覆盖旧结果。
- 准确账户回报率未来还必须引入账户日终快照和入金/出金流水；本期本金与可选操作数据不得被描述为已经足够计算完整收益。

### 5.8 R15、R17、R29：页面接入与未保存保护

- 新页面登记到 `pageRegistry`，使用 `LayoutHost`，提供 `settings-drawer` overlay，并按项目页面模板同步页面维护矩阵。
- 今日打卡、规则管理和历史记录是同一工作台三个业务页签；页签属于会话选择，不作为长期偏好强制保存。
- 规则管理复用今日打卡的主从排版：左侧是规则选择列表，右侧是所选规则的详情或编辑工作区；新建规则时右侧切换为空白编辑态，不使用规则编辑抽屉，也不以表格作为主操作界面。
- 取消“编辑区域宽度”和“规则内容默认高度/宽度”等用户配置与记忆交互，不写入 `user_preference`，页面设置中也不出现这些选项。右侧工作区宽度由主从布局响应式分配；规则内容编辑框按容器宽度换行、按内容合理增高并允许当次纵向调整，但不保存尺寸。
- 表格复用 `AppDataTable`、`AppTableColumn`、`AppPagination`；四态复用 `AppStateBlock`；历史详情/修正等辅助长流程仍可使用 `PageDrawer`，规则新建和编辑不使用抽屉。
- 页面设置抽屉只承载项目已有通用设置和本页真实消费的历史分页大小等业务选项；设置入口必须打开真实 `PageSettingsDrawer`，不允许保留无行为按钮或未消费的假配置。
- 离开页面、切换规则、切换日期或从规则编辑态切换上下文时，如存在未保存内容：打卡表单只提供“放弃修改/继续编辑”，规则编辑可额外提供“保存为规则草稿”；不得出现“保存打卡草稿”。提交或明确放弃后解除脏状态。
- 用户全局抽屉属于应用顶栏触发的视口级浮层，继续由 `App.vue` 承载；页面内部抽屉不得提升到视口级。

## 6. 数据与接口需求

### 6.1 PostgreSQL 核心业务实体

以下名称用于明确数据职责和关系，具体 DDL、索引及迁移拆分由开发计划确定；全部用户资产实体必须带归属列。

| 逻辑表 | 核心字段/关系 | 业务约束 |
| --- | --- | --- |
| `trade_discipline_rule` | 规则主体、名称、当前版本、状态、创建/更新时间 | 本人名下名称唯一；当前版本指向不可变版本 |
| `trade_discipline_rule_version` | 规则主体、版本、本金、名称快照、`effective_from_trade_date`、保存时间 | `(归属, rule_id, version)` 唯一，正式版本不可变；补录按生效交易日选择版本 |
| `trade_discipline_stock_rule` | 规则版本、稳定明细标识、名称、最大资金、内容、顺序、启用态 | 最大资金单条及合计受本金约束 |
| `trade_discipline_action_rule` | 规则版本、稳定明细标识、名称、一级类型 `buy|sell`、二级类型、保留换行的内容、顺序、启用态 | `buy → open_position|add_position`；`sell → liquidate|do_t`，版本内明细标识唯一 |
| `trade_discipline_checkin` | 规则主体、交易日、当前修订号、当前状态 | `(归属, rule_id, trade_date)` 唯一 |
| `trade_discipline_checkin_revision` | 打卡、修订号、规则版本、自评、无操作、未履约详细说明、普通复盘说明、首次/修正时间 | 每次正式提交形成不可变修订；未履约详细说明必填且保留换行 |
| `trade_discipline_reason` | 用户自定义原因标识、名称、启用/删除状态、创建/更新时间 | 当前用户私人候选；内置原因由系统定义、不混入用户可删除数据 |
| `trade_discipline_violation` | 打卡修订、内置原因码或自定义原因引用、原因名称快照 | 每个未履约修订恰好一条；打卡修订引用唯一；删除自定义原因不影响历史快照 |
| `trade_discipline_operation` | 打卡修订、股票代码/名称快照、方向、具体选股规则引用、具体买卖规则引用、财务字段、说明、顺序 | 两个规则引用都恰好一条且属于同一规则版本；同股可多条；财务字段可空但非负 |

为避免修正后 AI 输入漂移，操作、违规原因和规则关联都属于具体打卡修订，不能只挂在会变化的“当前打卡”上。

### 6.2 后续扩展实体边界

| 未来实体 | 用途 | 本期处理 |
| --- | --- | --- |
| 履约评估结果 | 保存规则引擎/AI 的独立判断、证据、输入签名和版本 | 不建调用链；核心表保留稳定关联条件 |
| 账户日终快照 | 现金、持仓市值、总资产 | 暂不创建业务入口 |

| 分析物化结果 | 履约率、违规分布、交易分布、收益序列 | 后续按原始事实重算，不写回核心记录 |

### 6.3 业务接口契约

接口命名可在开发计划中按现有 API 风格收敛，但必须覆盖：

- 规则：列表、详情、保存草稿/新版本、启用、归档/恢复、删除未启用草稿、复制。
- 打卡：今日摘要、按规则日期读取、首次提交、修正、历史分页、修订详情；本期没有打卡草稿接口。
- 未履约原因：读取“系统内置 + 当前用户自定义”单选候选、删除个人原因；不提供前端单独调用的新增动作，打卡写接口接受一个原因标识或一段原因文本。原因文本匹配不到可用候选时，后端在打卡事务内新增个人原因并返回其标识；接口拒绝空值、数组或多个原因。删除接口不得处理内置原因，已经使用的原因采用停用/软删除语义，历史仍可读取名称快照。
- 快捷打卡：独立动作，只接受规则引用和交易日，后端固定生成“已履约 + 无操作”，不能由前端伪装提交任意内容。
- 股票与交易日：交易日复用既有接口；股票输入使用 R31 专用轻量端点，不调用受 `stocks:view` 保护的 `GET /api/stocks`。
- 所有写接口返回最新版本/修订、业务状态和可展示消息；并发版本冲突返回可识别的 409，不静默覆盖。
- 历史列表采用服务端筛选、排序和分页；股票搜索须防抖并限制返回量。

### 6.4 一致性与事务

- 规则当前版本切换与版本/明细写入同一 PG 事务。
- 打卡首次提交或修正时，修订、违规原因、操作、规则关联和当前修订指针同一 PG 事务提交。
- 快捷打卡的重复请求必须幂等；已有记录时返回当前记录而非新增。
- 资金上限、规则关联、操作方向、交易日和归属均由后端再次校验。

### 7.1 页面 P1：交易纪律工作台

- **对应需求编号**：R1-R17、R26-R31
- **页面类型**：新增业务工作台
- **页面入口**：侧栏一级菜单“交易纪律”；用户中心快捷卡片跳转
- **原型文件**：[prototypes/trading-discipline-workbench.html](prototypes/trading-discipline-workbench.html)
- **页面布局**：
  - 布局事实源：对齐上述 HTML 原型。
  - 页头：标题、当前最新交易日摘要、页面设置入口。
  - 业务页签：今日打卡、规则管理、历史记录。
  - 今日打卡：规则状态栏为辅助选择区，右侧/下方主区承载履约表单与操作列表。
  - 规则管理：沿用今日打卡的主从布局，左侧规则列表负责选择和状态摘要，右侧直接承载详情/编辑；新建时右侧切换空白编辑态。选股和买卖规则是可重复明细区，规则内容使用完整换行的多行编辑器，不打开规则编辑抽屉。
  - 历史记录：筛选区 + 服务端分页表格；详情/修正使用页面级抽屉。
  - 关键操作：提交打卡、保存规则、启用、归档、复制、修正；均有 loading 和防重复提交。
  - 长内容：规则列表摘要可以截断，但规则编辑器和详情必须保留原始换行并完整展示；不能用摘要、tooltip 或省略号替代编辑正文。
  - 窄视口：规则选择区与表单上下排列；表格内部横向滚动，不让应用外壳滚动失控。
- **数据来源**：PostgreSQL 私人规则和履约数据；DuckDB 股票、行情交易日经既有 API 读取。
- **权限与可见性**：页面、页签、操作按钮按 R11、R28；403 显示权限态，不伪装为空态。
- **组件复用与通用能力**：
  - 已有：`LayoutHost`、`TradeDatePicker`、`PageDrawer`、`AppDataTable`、`AppTableColumn`、`AppPagination`、`AppStateBlock`、`AppRowActions`、`PageSettingsDrawer`、`v-permission`。
  - 可能新增：可复用的交易规则明细编辑器、消费 R31 的股票远程选择器；若项目中出现第二个消费场景，按复用规则抽取，不在页面内复制。
  - 配置化承载：页面默认信息密度和历史分页等通用展示字段按现有布局/组件配置链路保存；规则编辑区域宽度、内容编辑器尺寸、规则、日期和当次表单不写用户偏好。

#### 7.1.1 今日打卡

- **对应需求编号**：R4-R8、R10、R17、R26、R27、R30、R31
- **默认展示**：最新交易日、启用规则及其待打卡/已履约/未履约状态；有启用规则时选中第一条待打卡规则，否则选中第一条。
- **用户操作**：切换日期/规则、自评、无操作、增删操作、搜索股票、分别单选具体选股规则和具体买卖规则、在同一原因下拉框中选择或填写原因并行内删除个人原因、填写未履约详细说明和财务数据、提交或修正。
- **输入与校验**：遵守第 5.2、5.3 节；未履约原因及详细说明错误定位到原因区域，每笔操作的两个具体规则错误定位到对应操作行。
- **状态变化**：待打卡 → 已履约/未履约；再次提交 → 已修正。
- **保存/提交/取消**：提交前校验；存在脏数据时切换上下文需确认。
- **加载状态**：规则摘要与表单分区加载，已有内容刷新时不清空。
- **空状态**：无规则时引导新建；所选历史日无记录且存在当日有效规则版本时显示可补录空态，没有有效版本时明确阻止补录。
- **错误状态**：交易日、规则或表单加载失败局部显示错误和重试。
- **权限不足状态**：无查看权限接管整页；无维护权限只读展示。
- **数据刷新**：提交后刷新当前表单、规则状态和全局快捷摘要。
- **联动**：规则归档或版本变更后重新校验当前选择。
- **验收标准**：能覆盖四种组合——履约有操作、履约无操作、未履约有操作、未履约无操作。

#### 7.1.2 规则管理

- **对应需求编号**：R1-R3、R16、R17
- **默认展示**：采用与今日打卡相同的左右主从结构；左侧展示本人规则列表、状态和版本摘要并默认选中第一条可用规则，右侧展示所选规则的本金、资金分配、选股规则、买卖规则及操作区。
- **用户操作**：左侧切换规则；右侧进入/退出编辑，新建时右侧直接切换空白表单；可启用、归档/恢复、复制、删除纯草稿、去打卡，全程不打开规则编辑抽屉。
- **输入与校验**：实时展示已分配、剩余和超限；后端最终校验。
- **规则编辑器**：选股/买卖规则内容支持回车、空行和自动换行；买卖规则先选一级类型，再从受控候选选择二级类型。编辑区跟随右侧主区响应式宽度，内容框按内容合理增高并允许当次纵向调整；不提供宽度、高度或默认尺寸设置，也不记忆尺寸。
- **状态变化**：草稿、启用、归档；实质编辑生成新版本。
- **保存/提交/取消**：右侧编辑区提供保存草稿、保存并启用、取消；有脏数据时切换规则、页签或退出编辑必须确认。
- **空状态**：解释规则用途并提供“创建第一套规则”。
- **错误状态**：列表失败、详情失败和保存失败分别处理，不销毁已编辑内容。
- **数据刷新**：成功后刷新列表、今日摘要和选择候选。
- **验收标准**：资金合计超本金不能启用；旧打卡仍展示旧版本。

#### 7.1.3 历史记录

- **对应需求编号**：R9-R11、R28、R31
- **默认展示**：最近记录倒序、服务端分页。
- **用户操作**：筛选、分页、查看详情、切换修订、发起修正。
- **输入与校验**：日期仅真实交易日；股票筛选复用 R31 专用轻量端点。
- **状态变化**：修正成功后修订号增加，列表标记“已修正”。
- **加载/空/错误/权限状态**：复用通用组件标准四态。
- **数据刷新**：修正后保留筛选条件并刷新当前页。
- **验收标准**：能够查看任一历史修订的规则和操作快照。

### 7.2 页面 P2：用户中心全局抽屉增强

- **对应需求编号**：R12、R13、R28
- **页面类型**：更新现有视口级全局抽屉
- **页面入口**：应用顶栏用户头像

- **页面布局**：身份卡下增加今日纪律卡，退出登录仍位于抽屉底部；卡片内部显示摘要和规则行。
- **主次关系**：身份信息仍为用户中心主信息；纪律卡是快捷入口，不替代正式工作台。
- **关键状态**：加载、无启用规则、全部完成、有待打卡、失败、无权限。
- **权限与可见性**：严格按 R11、R28；不能为了显示红点绕过摘要接口权限。

#### 7.2.1 全局快捷无操作打卡

- **对应需求编号**：R13
- **默认展示**：仅待打卡且无冲突的规则显示快捷动作。
- **用户操作**：点击后确认规则和交易日，再提交。
- **输入与校验**：用户不能在快捷入口改变自评、日期或注入操作。
- **状态变化**：待打卡 → 已履约；重复点击幂等。
- **错误状态**：已有正式记录冲突时提示进入正式页面；网络失败保留按钮可重试。本期不存在打卡草稿冲突。
- **验收标准**：从任意授权业务页可在用户中心完成无操作履约，并同步工作台状态。

## 8. 边界条件与异常场景

| 场景 | 系统行为 |
| --- | --- |
| 没有任何规则 | 今日打卡显示引导；用户中心卡片显示“创建第一套规则” |
| 只有草稿规则 | 不计入每日启用规则总数，不允许正式打卡 |
| 多条选股资金之和等于本金 | 合法；剩余资金显示 0 |
| 金额合计因小数产生误差 | 以统一十进制定点金额口径校验，不使用浮点近似 |
| 规则在表单打开后被归档/更新 | 提交时返回冲突，不按旧客户端状态静默提交 |
| 最新行情日滞后现实日期 | 明确显示“数据最新交易日”，仍以数据接口 max 为准，不猜测现实交易日 |
| 交易日接口为空 | 禁止打卡，提示先完成行情数据同步 |
| 历史日期没有已生效规则版本 | 禁止补录，不允许用当前版本倒灌历史事实 |
| 已有正式打卡的历史版本后来被新版本替代 | 继续展示并修正原绑定版本，不自动迁移 |
| 股票停牌、退市或更名 | 已选代码可保存；历史展示名称快照，并可补充当前状态，不自动删除操作 |
| 已履约且无操作 | 合法 |
| 未履约且无操作 | 合法，但必须单选一个违规原因 |
| 未履约原因候选只有内置项 | 正常使用；用户可直接输入新原因，提交时自动新增 |
| 输入原因与本人已有原因归一化后相同 | 复用已有原因，不重复新增 |
| 删除从未使用的自定义原因 | 从后续候选移除；当前选中时清空输入并要求重新选择或填写 |
| 删除已经被历史使用的自定义原因 | 后续候选不再展示；历史修订继续展示保存时名称快照 |
| 未履约但详细说明为空 | 禁止提交并定位到详细说明字段 |
| 同股当日先买后卖或分笔操作 | 每笔独立保存，顺序稳定 |
| 财务字段不完整 | 允许提交，标记完整度；不生成伪精确收益 |
| 买卖规则一级类型发生切换 | 不合法的二级类型立即清空；用户必须重新选择合法二级类型 |
| 操作方向发生切换 | 已选具体买卖规则方向不匹配时立即清空并重新选择 |
| 具体选股/买卖规则候选各只有一条 | 对应选择器自动选中唯一候选 |
| 任一具体规则候选多于一条 | 对应选择器保持未选，必须人工选择后才能提交 |
| 任一具体规则候选为零 | 显示规则版本配置异常并阻止该操作提交 |
| 规则正文包含多段和空行 | 保存、版本快照、重新编辑和历史详情均保持原始换行，不折叠为单行 |
| 重复快捷请求 | 返回现有记录或幂等成功，不产生重复行 |
| 两个标签页同时修正 | 后提交者收到修订冲突并选择刷新，不覆盖新修订 |
| 公开/跨租户引用尝试 | 后端按归属返回 404/403，不泄露对象存在性和他人内容 |
| 页面局部接口失败 | 只阻断对应区域，已填写内容保留 |
| 交易纪律用户没有 `stocks:view` | 仍可通过 R31 专用端点搜索股票，但不能访问个股行情页面或其他股票接口 |
| 1100×620 视口 | 主从布局退化为上下结构，所有表单字段无需整页横向滚动即可访问 |

## 9. 性能、安全与兼容性要求

- 规则和单日操作规模较小，详情应一次读取完整修订；历史列表必须服务端分页，禁止一次加载全部历史。
- R31 股票远程搜索防抖、最多返回 20 条并取消迟到请求，避免逐字符高频扫描；后端拒绝空查询的大范围枚举和超限 `limit`。
- 今日摘要只返回规则标识、名称、状态和计数，不返回完整规则正文或操作明细；用户抽屉打开时按需加载，不常驻高频轮询。
- 金额使用精确定点数；接口和前端统一两位小数展示，不能用二进制浮点作为资金约束事实源。
- 所有写入校验归属、版本、交易日、规则关联和金额；自由文本按普通文本展示，禁止当作 HTML 渲染。
- 用户自定义未履约原因属于私人资产；新增、列表和删除必须带用户归属，原因名称与详细说明按普通文本处理。删除原因不得级联删除或改写历史履约事实。
- 不在日志、审计上下文或错误消息中完整记录用户的交易说明、股票操作清单和未来 AI 输入；审计只记录动作、对象引用、结果和必要摘要。
- 新页面必须验证 1100×620、1366×768、1440×900；1100×620 主从区提前退化为上下结构，只有历史表格自身允许横向滚动，打卡和规则表单不得整区横向滚动。
- 前端改动必须通过 `npm run build`；后端相关测试按 DuckDB 锁规则先检查并恢复服务状态；真实点击链路补充 Playwright E2E。
