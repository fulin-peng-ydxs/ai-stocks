## 2. 目标与已确认范围

目标是让用户日常只需“录成交 → 修改实际不符合项 → 补充漏买漏卖 → 提交”，系统完成金额汇总、持仓计算和履约分类，并为后续可视化保留可靠事实。

| 调整项 | 已确认目标 |
| --- | --- |
| 履约结果 | 移除整组履约自评选择，保留已履约、部分履约、未履约作为系统计算结果，用于回显、筛选和统计 |
| 逐笔判断 | 不再要求逐笔手选履约状态；根据系统核验和人工检查项生成逐笔结果，人工检查项默认符合，可按实际修改 |
| 持仓 | 新增独立真实成交与持仓账本，在现有交易纪律页面增加“现有持仓”页签，打卡顶部展示只读摘要 |
| 持仓限制 | 不填当日最大同时持仓数，不手选持仓超限；根据期初持仓和全日成交顺序自动计算并核对规则 |
| 成交金额 | 价格×数量自动计算，支持按交割单修正，保留计算值、实际值及金额来源；买入、卖出、费用分别汇总 |
| 未履约事项 | 买卖操作未履约直接来自操作，持仓超限等直接来自系统；仅漏买、漏卖需要补充股票和规则，不影响持仓 |
| 原因与说明 | 移除未履约原因、详细说明的填写及强制校验；保留选填复盘备注，不删除共享下拉及新增选项机制 |
| 修正范围 | 同一账户仅最新已提交交易日可修正，历史只读；修正重新核对持仓、资金和关联规则，不重复记账 |
| 历史重置 | 清理所有用户的交易纪律旧打卡及修订、历史规则版本；每套规则保留最新已发布正式内容重建为 v1，先备份再切换 |
| 初始化 | 各用户初始化真实期初持仓，空仓也明确确认；不能将最新一天成交当作期初持仓 |
| 数据稳定性 | 实际成交只记一次，规则评价可多份；保存稳定事实标识、修订、核验来源、计算口径版本和统计起算边界 |

本次建设必要的期初数据及持仓/资金调整承载，避免将送转股、转入转出等伪装成买卖。暂不开发完整收益图、券商同步、自动交易、自由文本规则自动解析、机会信号生成或多账户管理界面。初期使用每个用户的默认账户，数据保留账户归属。

## 3. 当前事实与必须替换的旧机制

| 当前事实 | 风险或影响 | 本轮处理 |
| --- | --- | --- |
| 打卡按用户、规则、交易日唯一，操作附属于打卡修订 | 同一真实成交可能在多套规则或多个修订中出现 | 成交账本与规则评价分离，多处评价不重复改变数量和资金 |
| 没有持仓账本，限制持仓时手填 `peak_positions` | 不能验证真实持仓，也不能准确统计峰值 | 初始化期初持仓，使用有序成交推导持仓及峰值 |
| 成交时间可空，页面按买入/卖出分组 | 分组顺序不等于成交顺序 | 实际成交时间必填，同一时间以显式顺序确定全日先后 |
| `assessment` 由用户选择，仅部分履约保存逐笔状态 | 判断口径和操作事实可能冲突 | 服务端统一计算，前端仅预览，不信任客户端结论 |
| 部分/未履约强制原因和详细说明，数据库有对应 CHECK | 只删除页面字段会导致写入失败 | API、服务、数据库约束、历史摘要和筛选一并调整 |
| 任意日期的打卡当前修订都能追加修正 | 修改较早交易可能破坏后续持仓 | 账户最新交易日约束覆盖页面、API和服务，不仅判断单条修订号 |
| 资金校验主要检查规则配置金额 | 配置通过不代表实际持仓未超限 | 建立实际占用核对；具体资金口径按第 10 章完成确认后实现 |
| 操作标识依附修订，表单提交会重新生成操作记录 | 不能直接作为跨修订的真实成交身份 | 增加稳定成交身份和有效修订关系，旧修订不重复参与计算 |

主要修改入口：`backend/api/trade_discipline.py`、`backend/services/trade_discipline_service.py`、`backend/storage/trade_discipline_repository.py`、`backend/storage/pg_ddl.py`、`frontend/src/api/tradeDiscipline.ts`、`TradeDisciplineView.vue`、交易纪律域组件及 `frontend/src/utils/tradeDiscipline*.ts`。

## 4. 业务与数据契约

### 4.1 真实成交、账户与规则评价

- 私人账户、期初数据、成交、调整事件、日结、评价和修订均按 `tenant_id + owner_user_id` 隔离，账户身份及归属由服务端解析。
- 一笔真实成交只有一个稳定身份；多套规则可以分别评价该成交，但持仓与资金只变动一次。旧修订只用于追溯，不能与有效修订一起累计。
- 账户按交易日统一提交成交事实并完成日结，规则打卡引用该日事实；前端可以按规则查看，不能分别录入重复成交来更新同一账户。
- 成交保存股票代码及名称快照、买卖方向、实际成交时间、同时间顺序、价格、数量、实际成交金额、计算金额、金额来源、费用和可选备注。价格、数量大于零，费用非负且允许零。
- 金额沿用十进制定点链路，自动金额按分舍入，不使用 JavaScript 浮点数作为记账依据。买入额、卖出额、费用和资金净流出分别展示，净流出按买入额减卖出额加费用计算。
- 买卖分组仅是展示方式。建仓/加仓、减仓/清仓可由操作前后数量辅助判断，自定义业务类型不能直接决定记账方向。
- 实际违反规则的成交允许如实记账并形成违规；卖出导致账面负持仓、重复成交、错归属等事实矛盾必须先解决，不能通过改选履约结果绕过。
- 支持记录“未按任何已设规则操作”，不强迫用户关联一条无关规则；其适用规则范围及评价归属在任务 L1 固化。

### 4.2 期初、持仓与日结

- 首次启用先确定起算交易日，录入期初股票及数量；明确空仓也是有效初始化。期初成本可缺失，缺失不得按零计算收益；需要账户收益统计时还必须具备期初现金和后续资金变动。
- 持仓由期初数据、有效成交和显式调整事件推导。禁止直接修改当前数量而不留下可追溯变动。
- 同股加仓不增加持仓只数，部分卖出不减少只数，数量归零后才减少。每日从期初开始，按全局成交顺序逐笔计算峰值。
- 示例：期初持有 A、B，先买 C 再清仓 A，峰值为 3；先清仓 A 再买 C，峰值为 2。两种情况期末都为 2，不能用期末数替代峰值。
- 无操作日延续持仓，并使用当日有效规则核对；规则降低上限后，已有持仓也可能形成当日独立违规。
- 区分总持仓和可卖数量；可卖规则以实施时核实的市场制度及交易日为准，不直接把总持仓当可卖，不仅依赖前端拦截。
- 保存日结的期初/期末状态、峰值、有效事件引用和计算版本，支持核对与复现；估值同时记录行情日期及来源，缺行情显示不可用，不按零估值。
- 非交易数量变化、现金流和分红等使用显式事件并保留日期、来源和原因。成本、现金不完整时不输出看似完整的账户收益率。

### 4.3 自动履约判断

服务端是最终计算入口，前端使用同口径预览。结果按当日、适用规则版本计算；不解析自由文本来猜测规则是否满足。

| 已完整核对的当日事实 | 系统结果 |
| --- | --- |
| 没有违规或遗漏 | 已履约 |
| 至少一笔合规操作，同时存在违规操作、漏买漏卖或独立的当日规则违规 | 部分履约 |
| 存在违规或遗漏，没有合规操作 | 未履约 |
| 无操作、无遗漏，已有持仓也符合规则 | 已履约 |
| 无操作，但存在漏买、漏卖或持仓超限 | 未履约 |

- 单笔存在明确违规，即为该笔未履约；不能将该笔其他符合项当成合规操作，凑成部分履约。只有一笔违规操作且无合规操作时，整体为未履约。
- 某笔买入造成持仓超限，违规归属该笔；期初持仓已超限则作为独立日级事实。通过稳定依据标识避免同一事实重复计数。
- 买卖操作未履约由操作自动汇总，股票、方向、时间直接取该操作，不增加第二次关联选择。
- 应买未买、应卖未卖由用户补充股票和对应规则；不生成实际成交，不变更持仓、金额或费用。
- “未履约事项必填”转为结果不变量：部分/未履约必须有结构化依据，自动依据即可满足，不能要求用户重复勾选。全部已履约无需填写偏差事项。
- 人工检查项默认符合，按实际修改；同时保存用户确认、系统核验等来源，预填不能冒充自动核验。填报不新增“未知”选项。
- 必需事实未能核对时，保留成交事实与评价完整性状态，显示待核对及缺失项，不能自动记为已履约；待核对数据不纳入正式履约率分母。三类履约结果与核验完整性分开保存。
- 保存所用规则版本、逐笔检查结果、结构化违规依据和计算口径版本。规则更新不改写既有评价，计算口径升级不得静默重算历史。

### 4.4 最新交易日修正与纠错

- 同一账户仅最新已提交交易日允许改变成交和持仓相关事实；无操作日也属于日结。不能仅检查某套规则最新打卡或某条记录的当前修订号。
- 账户级并发保护与乐观版本检查共同防止并发提交、重复点击、两套规则分别修改同一笔成交；失败不产生部分持仓或部分评价。
- 修正从该日期初重新计算，使用新有效事实替换旧修订的记账影响，并重新核对全部关联评价；旧记录保留用于审计。
- 已有后续日结时，禁止直接补插较早成交、改日期或删除旧事实来影响后续持仓。
- 较早日期发现错误时，提供受控地从最新日向前撤回、再按日期重填的路径，明确影响范围并保留追溯，不提供任意历史原地修改。

## 5. 页面设计与复用计划

### 5.1 入口与操作链路

- 保留 `/trade-discipline`，在现有工作台增加“现有持仓”页签，不新增侧栏菜单。初期只呈现默认账户，不增加账户管理流程。
- 今日打卡：只读持仓摘要 → 实际成交 → 漏买漏卖及选填备注 → 提交；履约结果显示为计算摘要，不再是表单选择。
- 现有持仓：展示股票、数量、可卖数量及具备输入时的成本、估值、浮盈亏；未初始化展示初始化入口，数量修正必须进入显式调整流程。
- 历史记录与修订详情：显示系统结果、核验完整性、操作和依据，支持按结果/事项筛选；移除原因选择与原因筛选，最新日才提供可用修正入口。
- 用户中心快捷无操作：复用同一账户日结、持仓和评价服务；有超限或遗漏时转正式核对入口，不直接写已履约。成功后刷新工作台、持仓、历史与共享摘要。
- 切换日期/规则/页签和离开页面继续使用既有未保存保护；保存失败保留草稿，明确区分试算持仓与已提交持仓。
- 本次触发页面设计闭环和组件/布局维护矩阵。旧原型含手选履约等过时交互，实施前更新受影响区域原型或设计说明；本轮不生成原型。

### 5.2 响应式设计

| 区域 | 核心内容 / 辅助内容 | 触发与降级 | 恢复入口、状态及滚动归属 |
| --- | --- | --- | --- |
| 页头与页签 | 当前日期、对象、提交/修正；辅助为状态解释 | 控制区宽度不足时自然换行，低高度不固定大块摘要 | 主操作保持可达，说明进入现有帮助入口，不改变当前选择 |
| 持仓摘要 | 已提交与试算数量、超限；辅助为金额分项 | 容器不足时分行，次要明细折叠 | 具名“持仓明细”入口恢复，草稿不重挂载，滚动交活动面板 |
| 成交表单 | 股票、方向、时间顺序、价格数量费用；辅助为说明和条件详情 | 继承现有主从降级，操作卡多列转单列，条件详情可展开 | 校验展开错误卡并定位字段，`AppScrollArea` 承接长内容，恢复宽度不清空输入 |
| 持仓/历史列表 | 股票数量、结果和关键操作；辅助为长说明 | 核心列优先，说明进详情，超宽只在表格内部滚动 | 明确详情入口，不改用户列偏好；分页与操作可达 |
| 初始化/调整/修订浮层 | 必填项、影响范围、提交取消；辅助为说明 | 复用受控弹层档位及正文内滚，不复制固定像素高度 | 关闭恢复触发位置，失败保留输入；窄视口仍可完成主流程 |

目标画像继续沿用工作台；具体断点由现有布局容器及组件契约承接，不新增无依据阈值。低高度优先让活动主区滚动，宽屏富余分配给持仓表、成交内容和规则核对。关键视口复核 `1100×620`、`1366×768`、`1440×900`，涉及宽屏分栏增加 `1920×1080`，新增局部断点检查临界两侧。

## 6. 实施步骤与进度

L1–L8 已完成本轮实现及本地验收；实际执行、范围和未验证边界见本节记录。依赖顺序为 L1 → L2 → L3 → L4，L5 承接后端契约；L6 可在 L2 后开发，但实际全用户清理必须在 L7 验证后、L8 切换窗口执行。

| 任务 | 工作与主要产出 | 依赖 | 完成条件 |

## 7. 全用户历史清理与切换

### 7.1 清理和保留清单

- 范围覆盖目标实例中所有租户、所有用户的交易纪律旧打卡、全部修订、操作快照及从属违规事实；清除旧规则历史版本和被替代的生效事件。
- 按用户、规则分别提取最新已发布正式内容，包含已发布但待生效的最新内容，重建为 v1；保留规则主体归属和名称。新生效边界与账本起算日协调，不继承旧事件导致版本空窗。
- 不把未发布草稿升级成正式版；草稿、归档状态及旧明细引用在预检保留清单中逐项核对，重映射引用，不擅自发布或恢复归档规则。只有草稿的主体不伪造正式版本。
- 原业务原因不再参与新写入，清理历史时处理其引用；不删除系统共享字典、公共下拉新增能力、账号、角色、菜单、行情或其他模块资产。
- 保留规则最新正式内容，不保留最新一天打卡冒充初始持仓。重置后各用户从未初始化开始，明确起算日后录入真实期初数据；新周期统计不伪造被清历史收益。

### 7.2 执行次序与失败处理

1. 核对服务、环境和实际 PG 目标，输出所有用户的影响计数、每套规则保留版本、待生效/归档/草稿冲突及引用清单；本轮授权不扩展到其他环境。
2. 生成可恢复备份并校验，保存目标身份、规则保留清单和恢复步骤；备份不进入 Git，不使用仅含计数的报告替代数据备份。
3. 暂停相关业务写入，按复合归属和外键关系执行重置/v1重建；处理主体指针、明细引用和激活事件，不仅删除版本表。全用户维护不等于取消每条记录的归属核对。
4. 完成后逐用户核对保留规则、v1明细、生命周期、旧记录零残留及非目标数据不变；记录一次性执行标识，重复执行不能再次清空新周期数据。
5. 启用新入口，验证初始化、实际成交、无操作、修正与权限态；恢复相关写入及原服务状态。
6. 失败时回滚未提交变更；已跨提交边界时按已验证备份恢复。新周期已产生数据后，不能仅回滚旧代码或重复运行清理，应先冻结写入并处理新数据与恢复点差异。

全用户清理只通过受控维护入口完成，不能复用只应删除测试前缀的 E2E cleanup，也不能放进普通启动初始化。不得对共享菜单/功能点做覆盖式“恢复”。

## 8. 验证计划与完成标准

### 8.1 领域、服务与 API

- 数量与峰值：期初空仓/非空仓、同股加仓、部分卖出、清仓、同日先买后卖/先卖后买、同时间顺序、无操作延续、负持仓拒绝、可卖限制及缺失初始化。
- 金额：定点舍入、交割单修正、零费用、价格数量非法、买卖汇总和净流出、修改后恢复自动金额；资金和成本不完整不生成假收益。
- 评价：全部合规、全部违规、一笔违规、一笔合规加漏卖、合规与违规混合、买入造成超限、期初已超限、无操作漏买漏卖、待核对不入履约率；相同依据不重复计数。
- 稳定身份：一笔成交被多套规则评价仍只记账一次；修订只计算有效事实，重复点击/并发请求/服务重试不增加成交和持仓。
- 修正：最新账户交易日允许、较早日拒绝、不能按规则绕过、不能补插历史破坏后续状态；故障回滚后数量/资金/评价均不变，撤回后可按日期重填。
- 权限：未登录、只读、仅提交、规则管理、无权限、跨账户/owner/tenant引用；新接口、股票搜索、初始化/调整和维护边界均需覆盖。
- 迁移与清理：新旧结构、约束替换、最新发布但未生效版本、归档/草稿、无正式版主体、多租户、外键、重复运行和备份恢复；真实用户与内置菜单不用于测试夹具。
- 规模：先以只读计数确定账户/成交及规则关联规模，补代表性全链路回归，覆盖读取、计算和落库；预检/清理避免逐行N+1和无界内存，不能只用算法小夹具证明上线可行。
